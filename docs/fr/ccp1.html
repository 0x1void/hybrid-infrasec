CCP1 · Administrer et sécuriser les infrastructures

Cette partie raconte la première étape du projet : la construction du socle sur lequel repose l’évolution présentée dans les chapitres suivants. Je l’ai reconstruit sur un nouvel hyperviseur Fedora 44, machine par machine, dans l’ordre imposé par les dépendances. Il est en service depuis le 2 octobre 2026, avec ses cinq VM, l’annuaire et le partage de fichiers.

Je décris d’abord la méthode, puis chaque étape de construction avec ses commandes, son critère de passage et les difficultés rencontrées. Viennent ensuite une fiche par machine, puis l’administration au quotidien, rangée selon les quatre compétences du certificat : les bonnes pratiques et les procédures d’exploitation (CP1), le réseau (CP2), les systèmes (CP3) et la virtualisation (CP4). Comme dans le reste du dossier, je ne cite que ce que j’ai réellement fait et vérifié. Quand l’exécution s’est écartée du plan de construction, je le dis et j’explique pourquoi. Ce que le laboratoire ne couvre pas est listé à la fin.

Les cinq VM tournent en même temps dans un budget mémoire fixé à 22 Go sur 32, ce qui laisse à l’hôte la marge dont il a besoin.

Pourquoi ces choix. KVM est l’hyperviseur intégré au noyau Linux : QEMU émule le matériel de chaque VM, et libvirt fournit une interface unique pour les définir, les démarrer, les sauvegarder et les relier aux réseaux. Fedora apporte un noyau récent, SELinux actif par défaut et Cockpit, dans la même famille que Red Hat Enterprise Linux, que l’on rencontre en entreprise. pfSense est un firewall libre très répandu dans les petites structures. Windows Server reste la référence pour l’annuaire. TrueNAS SCALE apporte ZFS, qui protège l’intégrité des données. Wazuh est un SIEM libre complet. Chaque brique est donc représentative de ce qu’on administre en production.

La méthode de construction

Un ordre dicté par les dépendances. Le LAN est isolé : rien n’y atteint Internet tant que le firewall ne route pas. Le contrôleur de domaine fournit ensuite le DNS et l’heure dont TrueNAS a besoin pour rejoindre le domaine. L’ordre de construction en découle :

pfsense-fw  ->  Win-Server-DC  ->  truenas  ->  fedora  ->  wazuh-siem
(passerelle)    (DNS, annuaire)    (joint AD)   (containers)  (SIEM)

Pendant les installations, chaque machine utilise pfSense comme passerelle et comme résolveur DNS. Dès que l’annuaire est en service, le DNS des serveurs bascule vers le contrôleur de domaine (10.10.10.10), parce que Kerberos a besoin de trouver ses enregistrements de service.

Un critère de passage par étape. Une machine n’est pas terminée tant que son test d’acceptation n’est pas vert : on ne passe pas à la suivante avec un critère rouge. Le critère est toujours un test qui prouve le service, pas un voyant : une résolution DNS qui répond, une jonction au domaine vérifiée, une métrique qui remonte.

Un snapshot à chaque critère validé. Deux types de points de restauration, toujours nommés de la même façon :

# VM : instantané à froid, pour un état cohérent
sudo virsh shutdown <vm>; sleep 25
sudo virsh snapshot-create-as <vm> <étiquette> "<description>"
sudo virsh start <vm>

# hôte : après tout changement de paquets, de réseau ou de SELinux
sudo snapper -c root create -d "POST-<OPÉRATION>-STABLE"

Un snapshot pris VM arrêtée est cohérent : aucune écriture n’est en cours. C’est indispensable pour le contrôleur de domaine, dont la base ne supporte pas d’être figée au milieu d’une transaction.

Étape 1 · L’hôte TeneT

L’hôte est la fondation de tout le reste : s’il est mal préparé, aucune VM ne démarre ou les disques se dégradent. J’ai donc traité son installation comme celle d’un serveur de production. Le disque est chiffré par LUKS dès l’installation de Fedora : si le poste est perdu ou volé, les disques des VM ne sont pas lisibles.

Les services de libvirt. Fedora 44 découpe libvirt en démons modulaires, activés à la demande par des sockets systemd. J’active chaque socket, puis j’ajoute mon compte aux groupes libvirt et kvm pour administrer sans être root à chaque commande :

for d in virtqemud virtnetworkd virtstoraged virtinterfaced virtnodedevd; do
  sudo systemctl enable --now ${d}.socket
done
sudo systemctl enable --now virtlogd.socket cockpit.socket firewalld
sudo usermod -aG libvirt,kvm "$USER"

Des sous-volumes dédiés. Les disques des VM et les couches des containers ont chacun leur sous- volume BTRFS, /vm et /var/lib/containers. Cela permet de les exclure des snapshots du système et de leur appliquer des options propres. La plus importante est l’attribut NOCOW (chattr +C). Un fichier qcow2 est réécrit en permanence ; sur un système de fichiers en copie à l’écriture, il se fragmente et les performances s’effondrent. L’attribut n’a pas d’effet rétroactif : il doit être posé sur le répertoire vide, avant la création de la première image.

sudo btrfs subvolume create /vm
sudo btrfs subvolume create /var/lib/containers
sudo chattr +C /vm /var/lib/containers
lsattr -d /vm /var/lib/containers        # doit afficher l'attribut C

Les deux sous-volumes sont montés par /etc/fstab, avec l’UUID du système de fichiers racine :

UUID=<UUID>  /vm                  btrfs  subvol=vm,nodatacow,noatime 0 0
UUID=<UUID> /var/lib/containers btrfs subvol=var/lib/containers,nodatacow,noatime 0 0
sudo systemctl daemon-reload && sudo mount -a
findmnt -t btrfs

SELinux, sans jamais le désactiver. C’est l’étape qui piège le plus : sans elle, aucune VM ne démarre, et libvirt ne mentionne pas SELinux dans son message d’erreur. Les images doivent porter le contexte virt_image_t. Je déclare la règle de façon permanente, puis je l’applique. Le répertoire n’est traversable que par son propriétaire et les services autorisés (chmod 711) :

sudo mkdir -p /vm/images /vm/iso
sudo semanage fcontext -a -t virt_image_t '/vm/images(/.*)?'
sudo restorecon -Rv /vm/images
sudo chmod 711 /vm/images
ls -dZ /vm/images          # attendu : system_u:object_r:virt_image_t:s0

La règle déclarée par semanage survit à un réétiquetage complet du système ; un simple chcon aurait été perdu au prochain restorecon.

Le pool de stockage. Un pool libvirt nommé tenet pointe sur /vm/images. Je l’ai testé de bout en bout avec une image jetable, qui doit hériter à la fois du contexte SELinux et de l’attribut NOCOW :

sudo virsh pool-define-as tenet dir --target /vm/images
sudo virsh pool-build tenet && sudo virsh pool-start tenet && sudo virsh pool-autostart tenet
sudo qemu-img create -f qcow2 /vm/images/test.qcow2 1G
ls -Z /vm/images/test.qcow2 && lsattr /vm/images/test.qcow2
sudo rm /vm/images/test.qcow2

Les deux réseaux. Le réseau default de libvirt (NAT, 192.168.122.0/24, switch virbr0) sert de WAN : l’hôte y joue le rôle de router et traduit les adresses vers Internet. Un second réseau, tenet, est un bridge isolé (br-tenet), sans routage vers l’extérieur : il porte le LAN 10.10.10.0/24, et sa seule sortie est le firewall. Je vérifie les deux avec sudo virsh net-list --all, qui doit les montrer actifs et à démarrage automatique.

Cockpit. La console web de Fedora remplace virt-manager. Depuis une seule interface, elle crée les VM, ouvre leurs consoles, gère les snapshots, les containers, le stockage et affiche les refus SELinux en clair, avec la correction proposée. Elle a un piège : à la création d’une VM, elle propose par défaut /var/lib/libvirt/images. Il faut choisir explicitement le pool tenet, sinon le disque perd à la fois le contexte SELinux et l’attribut NOCOW. Après chaque création, je contrôle donc ls -Z /vm/images et lsattr /vm/images/*.qcow2.

Snapper. L’hôte prend ses propres points de restauration. J’ai configuré Snapper sur la racine, avec une rétention bornée et ses timers, puis pris le point de référence du socle :

sudo snapper -c root create-config /
sudo snapper -c root set-config NUMBER_LIMIT=10 NUMBER_LIMIT_IMPORTANT=5
sudo systemctl enable --now snapper-timeline.timer snapper-cleanup.timer
sudo snapper -c root create -d "POST-SOCLE-FEDORA-TENET-STABLE"

Les sous-volumes /vm et /var/lib/containers ne sont pas inclus dans les snapshots de la racine : revenir en arrière sur le système ne fait jamais reculer les disques des VM, qui ont leurs propres snapshots.

Ce qu’il faut comprendre. KVM transforme le noyau Linux en hyperviseur : chaque VM est un processus QEMU, qui émule son matériel, et les instructions du processeur sont exécutées directement grâce aux extensions de virtualisation. libvirt pilote l’ensemble et fournit les réseaux virtuels. Un réseau NAT donne aux VM une sortie vers Internet derrière l’adresse de l’hôte, sans les rendre joignables depuis l’extérieur. Un réseau isolé n’a aucune sortie : c’est pour cela que le firewall doit être la seule machine reliée aux deux. Enfin, SELinux étiquette chaque processus QEMU et chaque disque : un processus ne peut ouvrir que les fichiers qui portent son étiquette.

Étape 2 · Le firewall pfSense

La VM. Je l’ai créée depuis Cockpit, dans le pool tenet, avec deux cartes réseau virtio : la première sur le réseau default (WAN), la seconde sur tenet (LAN). L’installateur Netgate installe pfSense CE. La VM a d’abord été créée sous le nom tenet-pfsense. Je l’ai renommée pfsense-fw pour garder la convention de nommage du laboratoire :

sudo virsh shutdown tenet-pfsense
sudo virsh domrename tenet-pfsense pfsense-fw
sudo virsh start pfsense-fw

Les interfaces. Depuis la console (menu 1, puis 2) : vtnet0 devient le WAN, en DHCP sur le NAT de libvirt (il obtient 192.168.122.95) ; vtnet1 devient le LAN, en 10.10.10.254/24. Je vérifie ensuite la sortie vers Internet depuis le shell de pfSense (menu 8) :

ping -c3 1.1.1.1
host cloudflare.com

Une fois l’installation confirmée, j’éjecte le média, pour qu’un redémarrage ne relance jamais l’installateur :

sudo virsh domblklist pfsense-fw                   # repérer le lecteur CD
sudo virsh change-media pfsense-fw sda --eject --config

L’assistant de configuration. Dans l’interface web (System → Setup Wizard), le firewall reçoit son nom, fw01, et son domaine DNS, infrasec.lab, distinct de la forêt Active Directory infrasec.local pour ne pas les confondre. Le mot de passe d’administration est saisi de façon interactive et n’est noté nulle part dans le dossier.

Les services du segment. pfSense porte le résolveur DNS du segment (Services → DNS Resolver, Unbound). Une fois l’annuaire en service, la zone infrasec.local est tenue par le contrôleur de domaine, et pfSense la relaie (PSSI, article 6.5). Il porte aussi le service NTP (Services → NTP) : c’est la référence de temps du segment, sur laquelle le contrôleur de domaine se synchronise.

La sauvegarde de sa configuration. L’export XML de pfSense (Diagnostics → Backup & Restore) est chiffré par une phrase secrète et rangé hors ligne. Il ne va jamais dans le dossier : il contient l’empreinte du mot de passe d’administration et la clé TLS de l’interface web. Cette reprise a été testée le 11 octobre (PV-04, annexe O) : après une modification témoin, la configuration complète a été restaurée depuis l’export en moins de cinq minutes, service vérifié de bout en bout.

Critère de passage. Depuis le LAN, Internet répond et les noms se résolvent. Depuis le WAN, l’interface d’administration est injoignable. Le lecteur CD est vide.

Un écart relevé plus tard. L’audit du 4 octobre a montré que l’interface d’administration répondait encore en HTTP sur le port 80, en plus de HTTPS (constat F-02). La correction est planifiée : forcer HTTPS et restreindre la source de gestion (annexe F).

Ce qu’il faut comprendre. pfSense est un firewall à états : quand une connexion sortante est autorisée, les réponses qui lui appartiennent sont acceptées automatiquement. Il suffit donc d’autoriser des sorties précises et de tout refuser en entrée. Le résolveur Unbound fonctionne par défaut en mode récursif : il interroge lui-même les serveurs DNS racine, sans dépendre d’un fournisseur. Donner au firewall un domaine DNS distinct de la forêt évite qu’un nom d’hôte du firewall soit confondu avec un enregistrement de l’annuaire.

Étape 3 · Le contrôleur de domaine

La VM. Windows Server 2025 tourne avec un disque et une carte réseau virtio, les plus performants sous KVM. Windows ne voit pas un disque virtio sans pilote : au moment de choisir le disque d’installation, je charge le pilote viostor depuis l’ISO virtio-win, montée comme second lecteur. J’ouvre la console Cockpit avant le premier démarrage, pour ne pas manquer l’invite de démarrage sur le CD.

Réseau et nom. En PowerShell administrateur, une adresse fixe, le DNS sur lui-même (le futur serveur DNS du domaine), puis le nom DC01 :

New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 10.10.10.10 `
  -PrefixLength 24 -DefaultGateway 10.10.10.254
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 127.0.0.1
Rename-Computer -NewName "DC01" -Restart

La promotion. J’installe le rôle AD DS, puis je crée la forêt infrasec.local avec le DNS intégré. Le mot de passe du mode de restauration (DSRM) est saisi de façon interactive : il ne passe ni par un fichier ni par l’historique.

Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
$dsrm = Read-Host -AsSecureString "Mot de passe DSRM"
Install-ADDSForest -DomainName "infrasec.local" -DomainNetbiosName "INFRASEC" `
  -InstallDns -SafeModeAdministratorPassword $dsrm -Force

Le serveur redémarre en contrôleur de domaine : il porte la forêt, le domaine, le catalogue global et la zone DNS intégrée à l’annuaire. Je vérifie l’ensemble avec quatre commandes, que je relance après chaque intervention :

Get-ADDomain | Select-Object Forest,DNSRoot,DomainMode
Get-ADForest  | Select-Object ForestMode,GlobalCatalogs
nltest /dsgetdc:infrasec.local
Resolve-DnsName infrasec.local

L’heure. Kerberos refuse toute authentification au-delà de 5 minutes d’écart. Le contrôleur de domaine est la référence de temps du domaine ; il se synchronise lui-même sur pfSense. Je n’avais pas réglé ce point au départ, et il a fait échouer la jonction de TrueNAS (INC-02, étape 4) : le fuseau horaire du contrôleur était mal réglé.

Les comptes. Un compte de service est dédié à la jonction de TrueNAS au domaine. Un groupe porte l’accès au partage de fichiers : les droits suivent les groupes, jamais les personnes. Les mots de passe sont saisis de façon interactive. Depuis INC-02, ceux des comptes utilisés sur plusieurs plateformes n’emploient que des caractères placés au même endroit sur les claviers français et américain (PSSI, article 5.4.3).

Une astuce de laboratoire. La console noVNC de Cockpit ne permet pas de coller du texte dans la VM. Pour éviter de retaper un script, je le sers depuis un autre nœud par un serveur HTTP temporaire et je l’exécute côté contrôleur. C’est réservé au laboratoire : en production, on passe par un partage d’administration ou un outil de déploiement.

Les agents. L’agent Wazuh s’installe par un MSI. J’utilise une installation qui attend la fin du programme, pour ne démarrer le service qu’une fois l’installation terminée :

Start-Process msiexec.exe -Wait -ArgumentList '/i','C:\chemin\wazuh-agent.msi', `
  'WAZUH_MANAGER=10.10.10.40','WAZUH_AGENT_NAME=Win-Server-DC','/qn'
Start-Service WazuhSvc
Get-Service WazuhSvc

L’exporter de métriques windows_exporter (port 9182) m’a demandé plus de travail. La version 0.31.8 a supprimé deux collecteurs que mon plan demandait (cs et logon) : le service s’arrêtait aussitôt démarré, sans message (INC-03). En le lançant au premier plan, j’ai obtenu l’erreur unknown collector cs, puis unknown collector logon. J’ai écrit un script qui teste le jeu de collecteurs, retire ceux que le service rejette, puis reconfigure le service. Le jeu retenu comprend ad et dns, propres au rôle de contrôleur de domaine :

msiexec /i windows_exporter.msi `
  ENABLED_COLLECTORS="cpu,logical_disk,net,os,service,system,memory,process,tcp,ad,dns" `
  /qn
Get-Service windows_exporter
Invoke-WebRequest http://localhost:9182/metrics -UseBasicParsing |
  Select-Object -Expand Content | Select-String windows_

Une règle propre au contrôleur de domaine. Il ne s’arrête jamais par virsh destroy : une coupure brutale peut corrompre la base Active Directory. Toujours virsh shutdown, et un snapshot à froid avant toute opération risquée.

Ce qu’il faut comprendre. Une forêt Active Directory contient un ou plusieurs domaines ; chaque contrôleur de domaine en porte une copie de la base. Le catalogue global permet de chercher un objet dans toute la forêt. Les clients ne trouvent pas le contrôleur par son nom : ils interrogent le DNS sur des enregistrements de service (SRV), comme _ldap._tcp.dc._msdcs.infrasec.local. C’est ce que vérifie nltest /dsgetdc, et c’est pourquoi tous les serveurs du domaine doivent utiliser le DNS du contrôleur. Kerberos authentifie par des tickets horodatés : au-delà de 5 minutes d’écart, un ticket est considéré comme rejoué et refusé. Le mode DSRM, enfin, permet de démarrer le contrôleur hors annuaire pour le réparer ou le restaurer : son mot de passe est un secret critique.

Étape 4 · Le stockage TrueNAS

L’installation et le réseau. TrueNAS s’installe sur le disque de 16 Go. Depuis sa console, je lui donne une adresse fixe 10.10.10.20/24, la passerelle .254 et le DNS du contrôleur de domaine, 10.10.10.10 : Kerberos a besoin du DNS du domaine pour trouver ses enregistrements de service.

Le pool. Dans l’interface web (Storage → Create Pool), le pool tank est un miroir ZFS sur les deux disques de données. Un miroir survit à la perte d’un disque. ZFS calcule une somme de contrôle sur chaque bloc : il détecte les erreurs silencieuses et les corrige depuis l’autre copie du miroir, à condition de lancer un scrub régulier.

La jonction au domaine. Dans Credentials → Directory Services, je renseigne le domaine INFRASEC.LOCAL, le compte de service dédié et son mot de passe, saisi de façon interactive. C’est là qu’est survenu le second incident.

Le second incident : la jonction refusée (INC-02). La première tentative a été refusée : « Time offset from the domain controller exceeds the maximum permitted value ». J’ai comparé les horloges depuis l’hôte avec virsh domtime. TrueNAS était à l’heure UTC exacte, le contrôleur de domaine avait plus de 5 minutes d’écart, à cause d’un fuseau horaire mal réglé. Après correction du fuseau et la synchronisation NTP du contrôleur sur pfSense, une seconde erreur est apparue : « The bind password is not correct ». Le mot de passe du compte de jonction avait été saisi sur deux dispositions de clavier différentes (QWERTY et AZERTY), ce qui donnait deux chaînes différentes. J’ai réinitialisé le mot de passe avec des caractères neutres, et la jonction a abouti. Le service Active Directory de TrueNAS est passé à l’état HEALTHY : royaume INFRASEC.LOCAL, keytab du compte machine créé, cache des comptes activé.

Ce qu’il faut comprendre. Avec deux disques de données, le miroir est la seule disposition redondante : chaque bloc est écrit sur les deux disques. ZFS écrit toujours les données modifiées à un nouvel emplacement (copie à l’écriture). Un snapshot est donc instantané : il fige la liste des blocs à un instant donné et n’occupe de place que pour les blocs modifiés ensuite. Il est en lecture seule, ce qui le protège d’une suppression ou d’un chiffrement par un rançongiciel côté client. Les ACL NFSv4 sont plus fines que les droits POSIX (héritage, droits séparés de lecture, d’écriture, de suppression) et correspondent aux ACL de Windows, ce qui les rend naturelles pour un partage SMB. La jonction crée un compte machine dans l’annuaire et une keytab, le fichier de clés qui permet à TrueNAS de s’authentifier par Kerberos.

Étape 5 · Le nœud de containers

                                   fedora

La VM. Fedora 44 Server, en adresse fixe 10.10.10.30/24, passerelle .254, DNS .10. Elle s’administre par Cockpit (port 9090) et par SSH. Elle sert aussi de poste d’audit : la VM Parrot prévue pour l’audit n’a jamais démarré, et l’audit du 4 octobre a été lancé depuis ce nœud.

Un compte sans privilège pour les containers. Les containers tournent sous le compte ais, sans droits root. Podman rootless s’appuie sur des plages d’UID et de GID déléguées à ce compte (/etc/subuid, /etc/subgid) : root dans un container correspond à un utilisateur sans privilège sur l’hôte. Le lingering systemd permet aux services du compte de tourner sans session ouverte :

sudo loginctl enable-linger ais
grep ais /etc/subuid /etc/subgid
mkdir -p ~/.config/containers/systemd

Des services décrits par des Quadlets. Chaque container est décrit par un fichier .container dans ~/.config/containers/systemd/. systemd en génère une unité utilisateur : démarrage automatique, redémarrage en cas d’échec, journaux dans journalctl. Ces fichiers sont la source de vérité : image, port publié, volumes, arguments. node_exporter illustre un cas particulier. Il doit lire le système de fichiers de l’hôte, mais on ne peut pas réétiqueter /proc ni /sys pour SELinux avec l’option :Z. Il partage donc le réseau de l’hôte et monte la racine en lecture seule :

[Unit]
Description=Prometheus node-exporter (rootless)
[Container]
Image=quay.io/prometheus/node-exporter:latest
Network=host
Volume=/:/host:ro,rslave
Exec=--path.rootfs=/host --collector.systemd
[Install]
WantedBy=default.target
systemctl --user daemon-reload
systemctl --user start node-exporter
systemctl --user status node-exporter
podman top node-exporter huser # l'UID réel sur l'hôte : pas root

La pile de supervision. Sur le même modèle tournent Prometheus et Grafana. Le plan prévoyait Prometheus sur son port habituel, 9090, mais Cockpit l’occupe déjà sur ce nœud : je l’ai publié sur 9091. Grafana écoute sur 3000. Zabbix, ajouté pendant l’évolution, interroge pfSense en SNMP. La configuration de la supervision elle-même relève de la compétence CP7 et est décrite au chapitre 6.1.

Le pare-feu local. firewalld n’ouvre que les ports nécessaires. Quand un port ne sert plus, je le ferme : celui de node_exporter (9100) a été retiré, puisque Prometheus l’interroge en local (constat F-05) :

sudo firewall-cmd --permanent --remove-port=9100/tcp
sudo firewall-cmd --reload && sudo firewall-cmd --list-all

Critère de passage. systemctl --user status actif pour chaque service, podman ps montre les containers, podman top … huser montre un UID non root, et les métriques répondent (curl -s localhost:9100/metrics | head). Le hardening de ce nœud est décrit avec la compétence CP3.

Ce qu’il faut comprendre. Un container rootless repose sur les user namespaces : l’UID 0 à l’intérieur du container correspond, sur l’hôte, à un UID pris dans la plage subordonnée du compte ais, sans aucun droit. Si un attaquant sortait du container, il se retrouverait avec un compte sans privilège, et non root. Pour la même raison, un container rootless ne peut pas, par défaut, écouter sur un port inférieur à 1024. Les Quadlets remplacent un outil de composition : c’est systemd lui-même qui démarre, surveille et relance les containers, comme n’importe quel service. L’option :Z d’un volume demande à Podman de lui donner une étiquette SELinux privée, lisible par ce seul container.

CP2 · Sécuriser le réseau

Un seul point de passage. pfSense est la seule VM reliée à la fois au WAN et au LAN. Côté WAN, aucune connexion entrante n’est acceptée par défaut ; la seule exception, le port du tunnel WireGuard, appartient à l’évolution du chapitre 5. Les refus sont journalisés, ce qui m’a servi de preuve pendant les tests.

Les services du segment. pfSense résout les noms (Unbound) ; la zone infrasec.local est tenue par le contrôleur de domaine et relayée par pfSense (PSSI, article 6.5). Il sert aussi de référence de temps. Les serveurs ont des adresses fixes, recensées dans le plan d’adressage de la PSSI (complément E.1).

Le filtrage à l’intérieur du segment. Le trafic entre deux VM du même segment ne traverse pas pfSense. Je l’ai donc limité sur chaque machine : firewalld sur les hôtes Fedora, pare-feu Windows sur le contrôleur de domaine. L’audit du 4 octobre le confirme : sur chaque hôte, la quasi-totalité des ports testés est filtrée, et aucun service ancien ou non chiffré (Telnet, FTP, SMBv1) n’est exposé (annexe B).

Diagnostiquer couche par couche. Pour les pannes réseau, ma méthode est la capture successive : WAN, puis compteurs de la règle, puis LAN (Diagnostics → Packet Capture). C’est elle qui a localisé en quelques minutes les deux défauts de l’accès distant (INC-06 et INC-07, annexe J). Elle m’a aussi appris qu’un test réseau doit partir du bon endroit : un essai lancé depuis l’hyperviseur, qui possède une route directe vers le segment, a « réussi » sans rien prouver (INC-05).

Ce que l’audit a relevé, et ce que j’en ai fait. Le socle n’est pas parfait, et je préfère le dire. L’hôte garde une adresse d’administration sur le segment de production, qui contourne le firewall (F-01). L’interface de pfSense répond encore en HTTP sur le port 80 (F-02). Le plan d’administration est joignable depuis tout le segment (F-06). Chaque constat a reçu une décision écrite : F-01 est accepté temporairement, avec une mesure compensatoire et une cible, un réseau d’administration dédié (mesure M-01) ; F-02 et F-06 sont planifiés (annexe F).

CP4 · Sécuriser la virtualisation

L’isolation par SELinux. SELinux reste en mode enforcing. Les disques portent le contexte virt_image_t, qui devient svirt_image_t quand la VM tourne : chaque VM reçoit ses propres catégories, ce qui l’isole des autres et de l’hôte. Si une VM était compromise, elle ne pourrait pas lire le disque d’une autre. Si une VM refuse de démarrer, je cherche le refus et je corrige le contexte : je ne désactive jamais SELinux.

Les réseaux virtuels. Le NAT de libvirt côté WAN et le bridge isolé br-tenet côté LAN. L’hôte possède encore une adresse sur ce bridge : c’est le constat F-01. Il a même faussé un test (INC-05), ce qui confirme la priorité d’un réseau d’administration séparé.

Les containers. Ils tournent rootless, sous un compte sans privilège, avec des user namespaces. Aucun socket de démon n’est monté dans un container, et aucun container n’expose un port privilégié (inférieur à 1024).

Les ressources. Le budget mémoire (22 Go sur 32) laisse à l’hôte la marge nécessaire ; free -h après chaque démarrage de VM permet de vérifier qu’il n’est pas dépassé. La supervision de l’hôte et des VM par Prometheus est décrite au chapitre 6.1.

La reprise. Chaque VM peut revenir à un snapshot nommé, l’hôte à un point Snapper, et la configuration de pfSense à son export chiffré. Le manuel d’exploitation classe ces retours arrière du plus léger au plus complet (annexe M, section 8) :

sudo virsh snapshot-list <vm>
sudo virsh snapshot-revert <vm> <étiquette>     # retour à un état connu
sudo snapper -c root list

Bilan du socle

Le socle a été construit dans l’ordre de ses dépendances, chaque étape fermée par un test et un snapshot. Il offre un seul point de passage filtré, une identité centralisée, un stockage contrôlé par groupes et un backup prouvé par une restauration. Le hardening est mesuré (Lynis 69 → 76) et chaque étape peut être annulée. Les trois incidents de construction ont chacun laissé une règle : le BIOS pour les installations par console web, l’heure synchronisée avant toute jonction Kerberos, la lecture des notes de version avant de déployer un exporter. Ses limites sont connues, écrites et rattachées à une décision : l’adresse de l’hôte sur le segment, l’administration encore trop ouverte, le SIEM qui ne couvre pas encore toutes les machines. C’est sur cette base, documentée et réversible, que j’ai pu concevoir et déployer l’accès distant Zero-Trust (chapitres 4 et 5) et gérer la sécurité de l’ensemble (chapitre 6).

How to read this pageHow I designed and delivered the remote access: the need, the constraints, four compared solutions, a three-year cost, then a controlled rollout with acceptance tests and a tested rollback. Figures show the choice; tables show the evidence.

2. Requirements

The full requirements document has the reference CDC-2026-01. This chapter summarizes it. The choice of solution and its cost are explained in chapter 4.

2.1 Context and existing system

INFRASEC’s whole information system runs on a single hypervisor. A pfSense firewall filters traffic and is the only way into the internal network 10.10.10.0/24. Behind it, the LAN switch connects an Active Directory domain controller (forest infrasec.local), a TrueNAS file server, a container server that runs monitoring (Prometheus, Grafana) and a Wazuh SIEM. There is no controlled remote access.

2.2 The need

In one sentence: let remote users reach, from the Internet, only the internal resources they need, without exposing the information system.

I identified two profiles, with deliberately different needs. The traveling administrator must reach the management plane to work remotely. The remote employee must reach the file share, and nothing else. This difference is the heart of the project: it is least privilege, the base of the Zero-Trust approach, applied to a real case.

2.3 Scope

In the project: the VPN server on the existing firewall, the two access profiles and their rights, the filtering rules per profile, key management and device enrollment, service monitoring, operations documentation and the revocation procedure.

Out of the project: redesigning the internal network (done in the first stage), client device posture, multi- factor authentication and firewall redundancy. The last two are kept for later.

3.2 Schedule and tracking

What sets the end of the project is not the technical work but the documentation: the fixed date is the report deadline, October 14. So I put the technical phases early. I also decided in advance what I would drop if I fell behind: the options (network monitoring with Zabbix, an extra detection rule) would be dropped before the report, never the other way around. In the end, both options were done on October 11.

Design (P1) and prototype (P2) overlapped on purpose. The prototype checked on the existing firewall that the planned solution worked, before the decision of October 6. Its incidents (INC-04 to INC-06) fed the deployment plan written on October 7.

To track the project, I used three simple tools. First, a coverage table that links each criterion of the framework to the deliverable that covers it, with its status. Second, the incident log (Annex J), where I write down each difficulty with its diagnosis, its cause and what I learned. Third, a snapshot at the end of each phase, named POST-[OPERATION]-STABLE, so I can go back at any time.

3.3 People

I ran this project alone, but with an organization. The security policy defines eight roles: CISO, system administrator, directory, network, storage, container operator, security analyst and auditor. I held them one after another, and I recorded each decision in the document that belongs to the role. When I write the engagement letter, I am the client of the audit. When I write the report, I am the auditor. When I compare that report to the letter, I am the client again. This separation on paper partly makes up for the fact that one person holds every role.

4. Why I chose this solution

4.1 Solutions studied

I studied four families of solutions: three VPNs that you host yourself, and one commercial ZTNA offer run by a provider.

WireGuard. A recent protocol with deliberately very short code (a few thousand lines, so it can be audited) and modern, fixed cryptography. It is built into pfSense. It is fast, uses little CPU, and it is free and open source. On the other hand, it is younger, and enterprise features such as multi-factor authentication are not built in.

OpenVPN. Mature, widely used, based on TLS, flexible, with many options including multi-factor authentication. It is heavier and slower, and its configuration is more complex, so it costs more to run and to audit.

IPsec / IKEv2. A recognized standard, often built into operating systems. Its configuration is known to be complex, it handles NAT poorly and it uses more resources.

Commercial ZTNA (offers like Zscaler Private Access or Twingate). The richest option: identity-based access, multi-factor authentication, no inbound port open. On the other hand, there is a subscription per user, a dependency on the provider, and traffic goes through a third party’s cloud. That is a sensitive point for GDPR and for control over the data.

What I take from this calculation. The two costs are close: €150 apart over three years, less than 4%. So cost does not decide, and I prefer to say it plainly. Two things still make a difference over time. First, the cost of WireGuard does not depend on the number of users, while the commercial subscription grows with each user: at thirty users, it would reach €2,160 per year. Second, with WireGuard no traffic goes through a third party, no data is handed to a provider, and no subscription ties the company down.

I also costed, separately, an option with an access point hosted in the cloud (a small instance, about €11 per month): €396 over three years. It is not required for the current need.

4.4 Chosen solution and architecture

I chose WireGuard on the existing pfSense firewall, with two profiles separated by least privilege. It is first in the matrix (4.85 out of 5), and it meets every constraint: no purchase cost, modern cryptography, efficiency, firewall integration, auditable code and full control over data.

This diagram sums up the security idea. An employee connection goes through three different checks. First the key: an unknown device gets no answer, and the port stays invisible to a scan. Then the firewall rule: only TCP 445 to the file server is open. Last, the directory rights on the share. None of these checks is enough on its own to open access: that is defense in depth. Two of these checks rely on pfSense, so its hardening, its backup and its monitoring are part of remote access security. The third depends on the directory and stays independent of the firewall.

The solution can grow easily. To add a user, I declare a peer and attach it to the rule of its profile. To add a profile, I create a rule. The architecture does not change.

5. How I organized the implementation

This chapter summarizes the deployment plan MEP-2026-01.

5.1 The framework: a controlled change

I relied on ITIL 4 practices for change management, release management and service validation. The evolution is a normal change: it changes what the information system exposes, so it must be assessed and then authorized before it is done. The assessment is based on the requirements, and the authorization is the approval of the deployment plan.

In the lab, the prototype and the target are in the same environment. I wrote the plan on October 7 from what the prototype had taught me, with a validation criterion for each step. Steps E0 to E7 were checked on the configuration that came out of the prototype. Steps E8 to E10 were done on October 11.

Once the service is live, adding or revoking a user becomes a standard change: approved in advance, repeatable, done by following a written procedure, without a full new assessment.

5.2 Impact analysis and prior backups

The change is additive: it adds an interface and rules, without touching the rules of the internal network. On the WAN side, a single port is open (UDP 51820), and WireGuard does not answer any unauthenticated packet. Before starting, I created three restore points: a snapshot of the firewall VM, an export of the pfSense configuration kept offline (it contains the hash of the admin password and the TLS key of the web interface), and a Snapper snapshot of the host.

A gap specific to the lab. pfSense’s WAN is connected to the hypervisor’s NAT network, so to a private address. I turned off the “block private networks” option on that interface to let the tunnel through. In production, the WAN has a public address and this option stays on.

What steps E3 and E4 taught me. At first, the two peers had the same Allowed IPs range. The tunnel came up, the status light was green, but the file server’s reply never got back to the employee, because no key “owned” their address. A packet capture showed where it stopped: the server answered, but the firewall sent nothing back into the tunnel. I fixed it with a unique /32 per peer (INC-06). The acceptance test then showed me that this fix was needed, but not enough: the tunnel interface had no fixed address, so pfSense had no return route to the clients (INC-07). Since then, a successful handshake is only a step for me. I only validate on real application traffic, observed end to end.

Choosing the test bench. My first test from the hypervisor “succeeded” without proving anything. The hypervisor has a direct route to the internal network (audit finding F-01), and the traffic went around the tunnel (INC-05). I then isolated the test client in a network namespace with no route to the internal network. That let me validate the handshake and find INC-06. The final acceptance test was run from a separate client VM, truly outside the protected network. For the deny tests to mean something, this client sends the whole 10.10.10.0/24 segment into the tunnel. Otherwise, forbidden traffic would never reach the firewall, and the test could not fail. I read the denials in the pfSense logs. The minute-by- minute detail and the captures are in PV-04 (Annex O).

5.5 Rollback

I start a rollback if access to internal services is lost, if a rule blocks production traffic, if the firewall becomes unstable, or if an essential criterion fails during the change window. I act from the lightest to the heaviest step: disable the tunnel (immediate effect, the internal network is not touched), remove the tunnel rules and the WAN rule, restore the configuration export, go back to the VM snapshot, then to the host’s Snapper snapshot. The goal is to get the previous service back in under one hour, as the RTO in the requirements asks. In almost every case, the first two actions are enough.

Updated documentation: the command handbook (WireGuard section: key creation, enrollment, troubleshooting, revocation), the bilingual operations manual (Annex M), the incident log (INC-04 to INC- 07), the awareness material (QR code rule) and the integrity register.

Handover. It relies on documentation that can be run as written: an administrator who did not build the project must be able to enroll, troubleshoot and revoke access without help.

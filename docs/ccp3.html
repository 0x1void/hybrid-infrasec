How to read this pageSecurity management, in three skills: measure (audit, EBIOS RM), apply a policy (PSSI, hardening, backup, awareness) and detect and handle incidents. The second half is the work done after the oral exam of 21 October 2026: each jury remark became a measured, proven fix.

6. Results: monitoring and cybersecurity management

A change is only safe if the infrastructure that receives it is watched, measured and able to react. This chapter shows what I did for that, skill by skill.

6.1 Infrastructure monitoring (CP7)

I split monitoring into two flows, because they answer two different questions. Metrics answer “is the infrastructure working?”. Prometheus pulls data from the exporters on the container server (node_exporter) and the domain controller (windows_exporter), and Grafana displays it. Security logs answer “is the infrastructure under attack?”. Wazuh agents send logs, file integrity and configuration compliance to the manager, which correlates them and raises alerts.

An alert tested for real. I created the “Target unreachable” rule in Grafana and tested it on October 11 (PV-04). At 13:11:18, I stopped the collection service on the container server. The alert went to Pending, then to Firing after the planned two minutes, and back to Normal when I restarted the service. A first try triggered nothing: a systemd service restarted the container in under one second. That was a good surprise about resilience, but I had to stop the service itself to test the alert. The other thresholds will follow the same model. Sending alerts by email is waiting for a mail server.

Useful dashboards. The domain controller has a dashboard that works with the recent version of windows_exporter (CPU, memory, disks, network, service state), chosen after the diagnosis of INC-03. Wazuh provides the threat hunting, compliance and MITRE ATT&CK mapping views that I used in PV-03.

Monitoring that is itself secured. The monitoring containers run without privileges (rootless Podman). I closed the node_exporter port on the local firewall, since Prometheus queries it locally (finding F-05). The web admin interfaces use TLS, except the firewall’s HTTP listener found in F-02, whose fix is planned.

Optimizing also means removing. I reduced windows_exporter to the useful, valid collectors only (cpu, logical_disk, net, os, service, system, memory, process, tcp, plus ad and dns for the domain controller). Less noise, no dead metric.

Network monitoring of the firewall. A firewall is a network device, so I query it over SNMP with Zabbix, the tool made for that. Zabbix runs in rootless containers and collects 100 items, including the tunnel state. SNMP v3 (authentication and encryption) is the goal. Version 2c, where the community string travels in clear text, is accepted in the lab only, with protections: a random community string, listening on the LAN only, and a firewall rule that allows queries from the Zabbix server only. I checked it: Zabbix gets an answer, the hypervisor is denied and the denial appears in the logs (PV-04).

6.2 Measuring and analyzing the security level (CP8)

I followed a full loop: engagement letter, then audit, then assessment of the report, then risk analysis, then treatment.

The engagement letter first (Annex A, October 1, 2026). Before checking anything, I wrote the mandate: context, objectives, scope (five components and the internal segment; the hypervisor and client devices are out of scope), reference frameworks (ANSSI, CIS, EBIOS RM, MITRE ATT&CK, GDPR), method, rules of engagement (active tests allowed, nothing destructive, no data taken out, a single point of contact), deliverables and compliance criteria. Written before the audit, it is then used to judge the report: you can only assess a report by comparing it to what was asked.

The EBIOS Risk Manager analysis (Annex D) treats the findings as real vulnerabilities. It identifies four business values, six supporting assets and seven feared events. It keeps four “risk source / target objective” pairs and describes four operational scenarios:

Before treatment, three scenarios are critical: ransomware on the SMB share (SO-1), compromise of the directory through RDP (SO-2) and a pivot to the hypervisor (SO-3). All three come from the same flaw: a management plane that is not isolated enough. The treatment plan has twelve measures, from M-01 (dedicated management network) to M-12 (Cockpit hardening). It relies first on what already exists (backup, SIEM, rootless containers). Once applied, it takes every scenario out of the critical zone. It is a target: today, the hardening measures (M-05 to M-09) are partly applied on the Linux server, and the isolation measures M-01 to M-04 are planned. So the pivot to the hypervisor (SO-3) remains the priority scenario, with a compensating measure. SO-1 and SO-2 will stay high, because their severity comes from the core of the system. They are accepted under watch: backup guarantees recovery and detection guarantees reaction.

The loop closes. Finding F-01 did not stay theoretical. It was the starting point of the simulated attack in PV-03, and then it skewed a remote access test (INC-05). What I take from it: an audit finding left untreated is a real attack path.

6.3 The security policy and how it is applied (CP9)

A twelve-article security policy (Annex E): purpose and scope, framework and references, organization and roles, asset classification, identities and access, network security and isolation, hardening of systems and containers, data protection, backup and continuity, logging, monitoring and detection, incident management (including escalation to CERT-FR and notification to the CNIL within 72 hours), secrets and cryptography, compliance and continuous improvement. I wrote the rules so they can be checked (“MUST”, “MUST NOT”), and I turned them into concrete procedures: command handbook, deployment plan, enrollment and revocation procedures.

Hardening that is measured, not just announced (Annex F). I fixed the Lynis findings on the Linux server, then I ran the audit again:

For the network findings, I made clear treatment decisions, as EBIOS workshop 5 requires. F-01 is accepted for now, with a compensating measure (isolated segment, a single operator, active Wazuh detection), until the dedicated management network exists. F-02, F-03, F-04 and F-06 are planned. Accepting a risk does not mean forgetting it: you decide it, you explain why, and you write down the date.

A 3-2-1-0 backup, and a proven restore (Annex G, PV-01). The SMB share has three copies: production on a mirrored ZFS pool, hourly snapshots kept for two weeks, and zfs send/recv replication to a second dataset. I simulated a total loss of the data, then restored from the snapshot:

The report also states its limits. In the lab, the replicated copy is on the same pool. In production, it would go to a remote server: the mechanism is the same, but the “2 media” and “1 off-site copy” criteria are only met in production. Also, restoring by simple copy does not keep ACLs, so I recommend a restore method that preserves them.

An awareness session designed to change habits (Annex H). The short session “Good security habits every day” lasts 45 minutes. It is for two audiences, users and the technical team, with vocabulary suited to each. It covers passwords, phishing, the workstation and remote access, data protection, and how to report an incident. To measure its effect, I plan a five-question quiz at the end, then a fake phishing campaign thirty days later. After incident INC-04, I added an instruction: a configuration QR code contains a secret key, and it must only be read with the WireGuard app.

6.4 Detecting and handling incidents (CP10)

The detection chain (figure 8) connects the Wazuh agents on the domain controller and the container server to the manager. The manager decodes the logs, applies rules, correlates and classifies events with MITRE ATT&CK. The response follows the security policy: detection, classification, containment, eradication, recovery, closure, then lessons learned.

An exercise: the brute-force attack of PV-03 (Annex I). I launched fifteen SSH login attempts on an account that does not exist, from the hypervisor’s management address (the F-01 vector), against the container server.

A real incident: a private key exposed (INC-04). While enrolling my smartphone, I scanned the administrator profile’s QR code with the camera app instead of the WireGuard app. The camera sent the content to an online search service: the private key had left the phone. I handled it as a real security incident, with the same chain. Classification: a secret tied to a privileged profile, so the key is considered compromised, without waiting for proof that it was used. Containment: I removed the old public key from the firewall right away. Eradication: new key pair, new QR code, enrollment redone with the right app. Recovery: handshake checked with the new key. Lessons learned: instruction added to the awareness session and to the handover. No part of any private key appears in this report.

This incident taught me more than an exercise. It proves in real conditions that revocation works (requirement EF5), and it shows that a human error is handled with the procedure, not by hiding it.

Keeping the evidence. The evidence of an incident is timestamped, sealed with a SHA-256 hash and kept offline. The security policy (article 10.5) covers how it is passed to analysts, escalation to CERT-FR, and notification to the CNIL when personal data is involved.

A threat watch that makes detection evolve (Annex K). It starts from the infrastructure inventory and prefers primary sources: CERT-FR, ANSSI, CVE and NVD, CISA’s Known Exploited Vulnerabilities catalog, vendors, MITRE ATT&CK, the CNIL. Each piece of information is qualified, then I decide (fix, compensate or accept), I record it in a register and, when an attack technique is involved, I turn it into a detection rule. One example: Wazuh’s default correlation tolerates eight failures in two minutes. For an infrastructure of this size, I deployed a stricter local rule (100100, level 12, five attempts in sixty seconds). I replayed the PV-03 attack on October 11: the alert fired in two seconds, from the fifth attempt, linked to MITRE technique T1110.001 (PV-04).

8.2 What the project taught me

A green light proves nothing. The WireGuard tunnel came up while no reply could get back to the employee (INC-06), and the acceptance test showed a second cause for the same symptom (INC-07). Today, I no longer take a displayed state as proof. I validate on real traffic, observed end to end.

An exposed secret is a compromised secret. When the key was read by the camera app (INC-04), the right decision was not to estimate the risk, but to revoke right away. It worked because the architecture makes revocation simple: removing a public key is enough.

Test from the right place. A test run from the hypervisor “succeeded” by going around the tunnel (INC- 05). A test that cannot fail teaches nothing.

Accepting a risk is a decision. I did not fix finding F-01 before the oral exam, because today it carries the only management path. I accepted it for now, explaining why, with a compensating measure, and the decision is dated in the freeze report (Annex F). That is very different from forgetting it.

8.3 Limits I own

  • The hypervisor’s management plane is still on the production segment (F-01), until the dedicated management network exists (M-01).
  • The dedicated vulnerability scan (OpenVAS) planned in the engagement letter was not run. Coverage was provided another way.
  • In the lab, the replicated backup copy is on the same pool. In production, it would go to a remote site.
  • The administrator profile rule still covers the whole internal segment. I need to limit it to the management interfaces, then retest this profile with the acceptance client.
  • Remote access has no multi-factor authentication yet, and SNMP is still version 2c (protected, but the target is v3).
  • Alerts show in Grafana but are not sent by email yet, for lack of a mail server.
  • Changing the Wazuh administrator password is still to be done.

8.4 Next steps

Short term: the dedicated management network and the removal of F-01 (M-01), narrowing the remote access administrator rule, restricting RDP (M-02), firewall administration over HTTPS only (M-04), and changing the Wazuh administrator password. Medium term: multi-factor authentication on remote access, SNMP v3, a regular vulnerability scan, automatic active response, sending alerts, and a Wazuh upgrade after testing. Later: a second firewall for redundancy (CARP) to go beyond the availability target, and taking client device posture into account.

8.5 Conclusion

This project took me from building an infrastructure to running it. I learned to turn a need into measurable requirements, to compare solutions with a method, to cost them honestly, to go to production without putting what exists at risk, and then to measure, decide and react. The results that matter most to me are the ones I can prove: a timed restore, a hardening index that goes up, an attack detected in under one minute, access revoked within one second, a real incident handled by revoking a key.

This report presents the work done on the Hybrid InfraSec lab for the certificate "Taking part in cybersecurity management" (CCP3) of the AIS title. After the oral exam of 21/10/2026, I went back to the lab for six days, from 21 to 26 October, with one simple rule: each remark from the jury had to lead to real work, measured and proven, not to one more paragraph.

1.3 Availability and security: the distinction I use

Security protects the confidentiality, integrity and traceability of information. Availability ensures the service answers when it is needed. In the classic triad, availability is part of security; but in operations, the two goals often pull in opposite directions. They are not opposed: they are designed together, and a good measure protects without breaking anything.

Situation The measure that broke the other goal The measure kept
Hypervisor Cockpit (INC-08) Binding the service to an address: the console disappears as soon as the network changes (availability lost). Restricting access with the firewall; the service listens everywhere, only the source is filtered.
SIEM certificate authority key (F-22) Destroying it: no certificate could ever be renewed (future availability lost). Keeping it in clear: confidentiality lost. Keeping it AES-256 encrypted, off the SIEM, in the host vault.
Hypervisor memory (F-23) Reducing all machines blindly: the SIEM, already tight, would have failed. Measuring each machine, reducing only the two oversized ones.
Account lockout (F-24) The lockout threshold protects against brute force, but a slow attacker can lock every account (denial of service). Keeping the threshold and making the lockout itself raise an alert (rule 100320).
Lab backup (PV-09) A backup that can be modified can be encrypted by ransomware. A read-only backup: available for restore, untouchable for an attacker.

4 · The INFRASEC organisation

4.1 The directory

The fictitious company INFRASEC has 10 employees in 6 departments. They are created in the infrasec.local directory by the idempotent script New-InfrasecCompany.ps1, from a single employes.csv file (PV-05). The script first ran as a simulation (-WhatIf), after a VM snapshot; its SHA-256 hash was checked on arrival on the controller.

  • 14 organisational units and 27 groups: 7 GG_ (6 departments and remote work), 10 DL_SMB_<share>_RW/RO, 8 ROLE_ mirroring the ISSP RBAC matrix; 10 computer objects.
  • 12 accounts: the 10 employees (random 24-character passwords, change forced at first logon, never displayed), adm.rj (separate admin account, the only one added to Domain Admins) and aud.externe (disabled outside audit missions).
  • Account separation: the everyday account rj has no admin rights; adm.rj administers; the built-in Administrator account is kept for emergencies and can no longer be reached over SSH (PV-07).

The SIEM received the 12 Windows 4720 account-creation events, all within two seconds. Finding noted: they arrive at level 8, below the alert threshold. Bulk account creation therefore remains a point to watch.

4.2 The AGDLP model

People join a global group (GG_: who they are), member of a domain local group (DL_: what it allows), the only group placed on the share's ACL. A newcomer only needs a group membership, never an ACL change.

4.3 The TrueNAS shares

The parent dataset tank/entreprise is not shared; Domain Users only has the right to traverse it, without inheritance. Five child datasets are shared over SMB: Commun, Direction, Comptabilite, RH, Projets. On each, DL_SMB_<share>_RW may modify, DL_SMB_<share>_RO may read, and nothing else is allowed.

Finding fixed

The TrueNAS SMB preset gave Domain Users the Modify right: all 12 domain accounts could write everywhere. A preset is not a policy. The ACL was brought back to least privilege, then proven with 6 accesses, including 2 expected denials (PV-05).

The shares are protected by recursive hourly ZFS snapshots, kept for two weeks. Restore was proven from the user's point of view: a file deleted by k.haddad came back in about one minute (PV-06). File access auditing is on for the 6 shares: we now know who did what, not only who logged on (F-20).

4.4 The password policy, enforced by both domains

The ISSP required 14 characters for users and 20 for privileged accounts. Both domains had stayed on the defaults: 7 characters and no lockout. Accounts complied with the ISSP because the script had generated their passwords, not because the domain enforced it. This is fixed since 26/10, identically in both domains (F-24):

Setting Ordinary accounts Administrators (PSO-Admins)
Minimum length 14 characters 20 characters
Lockout after 10 failures, for 15 min after 5 failures, for 30 min
Lifetime 365 days 180 days

The lockout was proven: 11 SMB logons with a wrong password give 10 failures then NT_STATUS_ACCOUNT_LOCKED_OUT, and event 4740 names the source machine.

5.3 Defects that keep coming back

Reading the 18 sheets again, four defects come back. They are the ones I learned the most from.

  1. A test that cannot fail. A DNS check that accepted error messages (F-14), a firewall test run from the target itself (F-15, PV-07), a "successful" gpupdate while the GPO did not exist (F-17), an "error-free" decryption that had produced an empty file (F-22). Rule drawn: before trusting a test, I check that it could have failed.
  2. An undeclared configuration. An address added by hand (INC-10), a pod started by hand (INC-09). Anything that is not in the configuration tool disappears at the first reload.
  3. An event seen but below the threshold. Persistence (level 5), agent stop (level 3), lockout (level 9), account creation (level 8). Seeing is not enough: the event must reach the level that raises an alert.
  4. A machine arriving without firewall or monitoring. The SIEM (F-15, F-16), the Samba controller (F-25). From now on, a machine enters the lab with its firewall, its agent and its monitoring.

6 · Detection and logs

6.1 Before and after the local rules

Three attack scenarios were played on the domain controller. In all three, Wazuh saw the event, but at a level below the lab's alert threshold (10). I wrote a local rule for each, validated with wazuh-analysisd -t before reloading, then replayed the attack.

Key point

The path filter of rule 100300 ignores case: Wazuh records Windows paths in lower case, which is why the dashboard search found nothing. When the interface shows nothing, I read the raw log (grep in alerts.json).

6.2 The SIEM watched in turn

A stopped SIEM raises no alert: it is the worst kind of silence. After INC-11, the manager restarts on its own after a failure, and Zabbix checks its API (55000) and agent reception (1514) every minute, with an alert after three consecutive failures. The SIEM disk is watched by Prometheus, with a Grafana alert above 80 %, before the indexer thresholds (85 %, then blocking at 95 %).

6.3 Log retention and sealing

I measured before deciding: about 8 MB of raw alerts a day, 113 KB once compressed, 4.4 MB a day in the indexer. The searchable copy is kept 90 days (indexer ISM policy), the sealed raw copy 365 days. Sealing runs every day at 00:30 UTC with Persistent=true: since the lab is off at night, the timer catches up the missed day at the next boot. The catch-up was proven on 26/10.

7 · Continuity and backup

7.1 Why a second domain

The Windows controller runs an evaluation version, which expires around 27/03/2027. On that date, the directory would stop: no more authentication, no more shares. So I built a continuity domain, infrasec.internal, on a Samba 4.22 controller under Debian 13 (lnx-dc01), with the same company and the same policy.

7.2 What is in place (PV-08)

  • The same company: the bash script infrasec-samba-societe.sh replays the same employes.csv (same hash, 7228c38a…). Simulation first, then the real run; a second run recreates nothing (idempotence proven).
  • The same monitoring: Wazuh agent 003, same version as the manager, held against upgrades.
  • The same filtering: ufw, one rule per legitimate flow, NetBIOS closed (F-25).

7.3 The migration, written before it is needed (PROC-01)

The procedure sets the steps from D-30 to D+30, with a risk register and a roll-back possible until D+30. Its success criterion is measurable: the 6 test cases of PV-05 give the expected result on the new domain, and a failed logon there raises the matching Wazuh alert.

7.4 The lab backup (PV-09)

No full backup of the lab existed apart from the VMs' internal snapshots. With no external disk, I ruled out repartitioning the host disk: shrinking an encrypted partition is the riskiest possible operation on that disk. Instead, I built an immutable local level, using the existing /vm BTRFS subvolume.

The inventory beforehand avoided two traps: wg-client was stored outside /vm and depended on a base image, and /vm/iso held 55 GB of useless images, deleted one by one after checking. After the backup, lab-backup list shows both parts read-only, lab-backup verify recomputes every hash, and a write attempt by root is refused (Read-only file system).

Stated limit

This level protects against mistakes, corruption and ransomware. It does not protect against failure or theft of the host disk. The command lab-backup export /dev/sdX is ready: it will copy the latest backup to a LUKS2-encrypted USB disk as soon as one is available.

8.2 Remaining work

  • External copy of the backup: the lab-backup export command is ready; the USB disk is missing.
  • Log hashes off the SIEM: root on the SIEM could change both the logs and their seals.
  • Prune the Windows controller's internal snapshots: 17 snapshots take 124 GB on the host for a 60 GB disk.
  • pfSense: replace ISC DHCP, now end of life, with Kea.
  • Bulk account creation: raise the grouped 4720 event above the alert threshold.
  • Separate administration network (measure M-01): the host still has an address in the LAN it administers.

8.3 What I take away

I take away three habits. I prove a fix by replaying the test that revealed the defect, from a third machine. I read raw logs when the interface shows nothing, and I read those of the right boot. And I always state exactly what a measure protects against, and what it does not: that is what lets security and availability work together instead of against each other.

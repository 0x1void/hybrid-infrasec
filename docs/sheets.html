INC-08 — Availability: the hypervisor Cockpit is unreachable outside the home network

Finding date: 21/10/2026 · Fix: 23/10/2026
Asset: hypervisor HV01 (host TeneT, Fedora Linux 44) — service cockpit.socket, host firewall (firewalld, zone public)
Impact: loss of the hypervisor's web administration console; the VMs and their services are not affected. Administration continued through the emergency access (virsh / virt-manager on the local console).

Symptom

Connected to a smartphone hotspot instead of the home network, the host no longer offers Cockpit, neither from the network nor locally (https://localhost:9090).

Diagnosis

  1. systemctl cat cockpit.socket: a local drop-in file replaces the default listening — ListenStream= (reset) then ListenStream=192.168.1.188:9090.
  2. ss -tlnp | grep 9090: Cockpit only listens on 192.168.1.188:9090, the host's address on the home network.
  3. firewall-cmd --list-all: the cockpit service is not open to the whole zone; a rich rule allows it from 192.168.1.0/24 only.

Root cause

Two hardening measures stacked, one of them in the wrong place. The firewalld rule restricts who can reach Cockpit: that is the right level. Pinning the listening to an address also ties the service's availability to one specific network: on another network the address no longer exists and Cockpit listens nowhere, not even locally.

Resolution

systemctl revert cockpit.socket (removal of the local override), daemon-reload, socket restart. The firewalld rule is kept: remote access stays limited to the administration network.

Proof

  • No local drop-in; original unit /usr/lib/systemd/system/cockpit.socket: ListenStream=9090.
  • ss: listening on *:9090.
  • curl -skI https://localhost:9090 → HTTP/1.1 200 OK; console open on localhost:9090.
  • Rule kept: rule family="ipv4" source address="192.168.1.0/24" service name="cockpit" accept.
  • Real-conditions test (23/10, 23:52-23:54), laptop on the phone hotspot (wlo1 = 172.20.10.2):
  • before (old address): 192.168.1.188:9090 → The connection has timed out (the address does not exist on this network);
  • after: https://localhost:9090 open, terminal available.

Lesson

(1) Access is restricted at the firewall, not by binding the service to an address: the first measure protects, the second only breaks availability. (2) Hardening is tested on every network where we actually work. (3) A documented, proven emergency access (local console, virsh) is what let work continue: security and availability are designed together.

INC-09 — Monitoring: the Zabbix pod does not restart with the VM (deployed outside systemd)

Date: 23/10/2026
Asset: VM fedora (10.10.10.30), rootless user ais — pod zabbix (zbx-db, zbx-server, zbx-web)
Impact: SNMP monitoring of the fw01 firewall interrupted (blind spot); no data loss. Prometheus, node-exporter and Grafana not affected.

Symptom

After the fedora VM restarted, the Zabbix web interface (port 8080) no longer answers. podman ps -a shows the pod's three containers Exited (0) 2 days ago, while prometheus, node-exporter and grafana are Up 18 minutes: they restarted on their own.

Diagnosis

  1. systemctl --failed: no failed unit. The pod does not crash: it is simply not started.
  2. loginctl list-users: Linger=yes for ais, so user services start at boot with no open session.
  3. ls ~/.config/containers/systemd/: Prometheus, node-exporter and Grafana are declared as Quadlet files (*.container), turned into systemd services at boot (grafana.service: generated). The zabbix pod, created by hand twelve days earlier (podman pod create / podman run), has no Quadlet file.

Root cause

Inconsistent deployment of the monitoring chain: three components declared to systemd, one started by hand. Nothing restarts the latter at boot.

Related finding (gap with the ISSP, art. 11 — secrets)

podman secret ls empty: the PostgreSQL password was passed as a clear-text environment variable, so readable with podman inspect and probably present in the shell history.

Resolution

  1. Return point: VM snapshot pre-zabbix-quadlet (virsh snapshot-create-as).
  2. Password moved into a Podman secret zbx-db-password without being displayed (podman inspect … | sed … | podman secret create zbx-db-password -).
  3. Pod described in Quadlet: zabbix.pod, zbx-db.container, zbx-server.container, zbx-web.container (dependencies Requires=/After=, Restart=always, WantedBy=default.target, Secret=…,type=env). Validated with quadlet -dryrun -user before any switch-over.
  4. Switch-over: podman pod rm zabbix (the named volume zbx-pg is kept), daemon-reload, start.

Secondary incident during the switch-over: SELinux denial

zbx-db stops at once: chmod: /var/lib/postgresql/data: Permission denied, although the files belong to 70:70 (the image's postgres user) inside the namespace. The audit log confirms it:
avc: denied { setattr } comm="chmod" name="_data" scontext=…container_t:s0:c272,c377 tcontext=…container_file_t:s0:c125,c516 permissive=0
The types are right; only the MCS categories differ: the volume carried the private label of the old container. Fix: the :Z option on the volume (Volume=zbx-pg:/var/lib/postgresql/data:Z), which relabels it for its new owner. SELinux stays enforcing.

Proof

  • After the switch-over: the four units active (running), curl -sI http://127.0.0.1:8080 → HTTP/1.1 200 OK, PostgreSQL database system is ready to accept connections (WAL recovery done, no loss).
  • podman inspect zbx-db … | grep -c '^POSTGRES_PASSWORD=' → 0: the password no longer appears in the container configuration.
  • Non-regression test: full stop and start of the VM; at up 1 min, the seven containers (including zbx-db, zbx-server, zbx-web) are Up with no action, and the interface answers 200 OK.

Functional check

Zabbix → Hosts: fw01 (10.10.10.254:161) available over SNMP, 100 items collected. The "Packet filter reason codes" graph shows a collection gap (blind spot) then values resuming at 23:14, right after the switch-over.

False alarm open for 12 days (related finding)

Since 11/10 the dashboard showed "Linux: Zabbix agent is not available" on the Zabbix server host: the "Linux by Zabbix agent" template expected an agent on 127.0.0.1:10050, while no agent is deployed. Yet the architecture splits the roles: Prometheus and node-exporter monitor Linux, Zabbix monitors the firewall over SNMP. Fix: template unlinked and cleared ("Unlink and clear", 121 → 78 items), agent interface removed; only "Zabbix server health" (internal items) is kept. "Host availability" widget extended to SNMP; Geomap widget removed (no location set). Result: 0 problems, 78 triggers with 0 in problem state, fw01 "Available".

Closing the "clear-text secret" finding

  • PostgreSQL password rotation: new random 32-character password, generated in a shell variable, passed to psql on standard input (ALTER ROLE), then written to the secret (podman secret create --replace); never displayed. Restart of zbx-server and zbx-web: database connection with no error, HTTP/1.1 200 OK.
  • Shell history: 5 lines contained the old password (grep -c 'POSTGRES_PASSWORD=' ~/.bash_history → 5), which confirms the exposure; removed (→ 0).
  • Volumes: no orphan volume left; remaining prometheus-data, grafana-data, zbx-pg, zbx-export, zbx-snmptraps.

Lesson

(1) A service is in production only if it is declared: any container started by hand is a delayed incident; the rule becomes "one service = one versioned Quadlet file". (2) An access denial while Unix rights are correct is read in ausearch -m AVC: we fix the label, we do not disable SELinux. (3) The proof of a restart fix is a restart. (4) A secret in an environment variable is an exposed secret: podman secret separates the value from the configuration, and an exposed secret is changed (rotation), not hidden. (5) An alert left open with no action no longer informs anyone: the monitoring scope must match the architecture.

INC-10 — Change F-13: the host loses its address on the lab LAN (non-persistent configuration revealed)

Date: 24/10/2026, 01:11 → 01:20 (outage: about 8 minutes)
Asset: hypervisor HV01 (host TeneT) — bridge br-tenet, NetworkManager connection br-tenet
Impact: the host can no longer reach any lab service (Cockpit on fedora, TrueNAS, Wazuh API, Grafana, Zabbix, pfSense); the VMs keep running and keep talking to each other. No data loss.
Originating change: fix of F-13 (nmcli con mod br-tenet connection.zone lab-tenet then nmcli dev reapply br-tenet), preceded by the snapshot PRE-F13-ZONE-LAB.

Symptom

A few minutes after the change, every lab web interface times out (Connection has timed out, API is down, NetworkError). ping 10.10.10.30 from the host: 100 % loss.

Diagnosis (service first, then cause)

  1. Hypothesis 1, VM ports detached from the bridge by the reapply: ruled out. ip -br link show master br-tenet lists the 5 LAN-side ports (vnet2, vnet3, vnet4, vnet6, vnet8), all forwarding (bridge link).
  2. Hypothesis 2, the new zone blocks replies: br-tenet put back into public live; the ping still fails. The zone is not the cause.
  3. ip -br addr show dev br-tenet: the bridge is UP with no address; no more 10.10.10.0/24 route. nmcli con show br-tenet: ipv4.method: disabled, ipv4.addresses: --.

Root cause

The host address 10.10.10.2/24 had never been declared in NetworkManager: it had been added by hand (ip addr add), as the 10.10.10.0/24 route without a metric already showed (routes created by NetworkManager carry one). The reapply put the connection back in its declared state, with no address. The same weakness existed at every host reboot.

Recovery and fix

  1. Recovery: ip addr add 10.10.10.2/24 dev br-tenet → ping 0 % loss, Zabbix HTTP/1.1 200 OK.
  2. Isolated test of the zone: br-tenet put back into lab-tenet live → ping still 0 % loss, Zabbix 200 OK. The closed zone does not hinder the host's outbound connections.
  3. Lasting fix: address declared in NetworkManager — ipv4.method manual, ipv4.addresses 10.10.10.2/24, ipv4.never-default yes (the bridge never becomes the default route), ipv6.method disabled; reapply replayed on purpose: address present, zone lab-tenet, ping 0 % loss.

Lesson

(1) A "minor" change on the host network (firewall zone) revealed an undeclared configuration: anything that is not in the configuration tool disappears at the first reload. Rule: no hand-made network configuration on the host, everything goes through nmcli. (2) Diagnosis by elimination: one hypothesis at a time, each checked with a command (bridge ports, zone, address), without touching the VMs. (3) The service is restored first (address put back live), the cause is fixed next (persistent configuration), then the fix is proven by replaying the action that caused the outage. (4) The return point PRE-F13-ZONE-LAB existed; it was not needed, because the cause was found in under ten minutes.

INC-11 — Detection: the Wazuh manager fails at boot, SIEM blind for 3 h 10 with no alert

Date: 23-24/10/2026 · Times in UTC (SIEM logs), Paris time in brackets
Asset: VM wazuh-siem (10.10.10.40, Ubuntu 26.04.1 LTS, Wazuh 4.14.8) — service wazuh-manager (analysis, API 55000, agent reception 1514)
Impact: from 20:17 to 23:27 UTC (22:17 → 01:27), no agent event is analysed and no alert can be raised. The indexer and dashboard run: the interface displays, but shows [API connection] API is down. No monitoring reports the outage.

Symptom

24/10 at 01:16 (Paris), the Wazuh dashboard shows API is down and Error getting the authorization token.

Diagnosis

  1. Session at 01:49: systemctl is-active wazuh-manager wazuh-indexer wazuh-dashboard → active ×3; api.log: wazuh-wui authentications with 200. The service works in the current boot; the outage is earlier.
  2. journalctl --list-boots: four boots on 23/10 (UTC) — -3 20:17:02 → 23:27:20, -2 23:27:24 → 23:28:18, -1 23:28:20 → 23:37:12, 0 since 23:49:41. The symptom (23:16-23:21 UTC) falls in boot -3.
  3. journalctl -u wazuh-manager -b -3: wazuh-apid: Process 1485 not used by Wazuh, removing... → Killed → wazuh-apid did not start correctly → Failed with result 'exit-code' (20:17:10, after 3.4 s).
  4. journalctl -u wazuh-indexer -b -3: indexer started at 20:17:17, active until 23:27:17. Only the manager was missing.
  5. Boot -1: manager started normally at 23:28:24; the service came back with the VM restart at 23:27, not through a corrective action.

Root cause

A PID file left by an unclean shutdown pointed, at the next boot, to a process number reassigned to another program. The Wazuh start script removed that process, the API did not start and the whole manager stopped in failure. Two defects turned this one-off failure into a three-hour outage:

  • no automatic restart: the wazuh-manager.service unit has no Restart=; a failure at start stays a failure;
  • nobody watches the SIEM: Prometheus scrapes localhost and the domain controller, Zabbix the firewall over SNMP; neither the API (55000) nor agent reception (1514) is checked.

Fix

  1. Automatic restart (systemd override, without touching the package unit): /etc/systemd/system/wazuh-manager.service.d/restart.conf → [Service] Restart=on-failure RestartSec=30; daemon-reload. Check: systemctl show wazuh-manager -p Restart -p RestartUSec → Restart=on-failure, RestartUSec=30s.
  2. SIEM monitoring in Zabbix: host wazuh-siem, two Simple check items from the Zabbix server (fedora), every minute — net.tcp.service[tcp,10.10.10.40,55000] (API) and net.tcp.service[tcp,10.10.10.40,1514] (agent reception), value 1 at rest. Two High severity triggers: max(…,#3)=0, i.e. three consecutive failures (an incident or a 30 s automatic restart raises no false alarm).

Detection test (24/10, Paris time)

  • 02:18:50: systemctl stop wazuh-manager → inactive (clean stop: Restart=on-failure does not restart, which allows the test);
  • 02:21:13 and 02:21:14: problems SIEM: Wazuh API unreachable (55000) and SIEM: agent reception stopped (1514), High severity, on the dashboard;
  • 02:38:12: systemctl start wazuh-manager → active. Detection delay: 2 min 23 s, against 3 h 10 with no alert during the incident.

Related finding: administration access to the SIEM lost

The password of the ais account on wazuh-siem was recorded in no password manager. Recovered through the out-of-band console (KVM): boot with rw init=/bin/bash, passwd ais, reboot. Trap met: in this rescue shell the keyboard is QWERTY. The new password is stored in the manager.

Lesson

(1) A security service that can fail at boot must restart on its own; otherwise a few-second incident becomes an outage of several hours. (2) The detection tool itself must be monitored: a stopped SIEM raises no alert, the worst kind of silence. (3) We read the logs of the right boot: journalctl --list-boots first, then -b -N. (4) Admin accounts go into a password manager as soon as they are created.

F-13 — The hypervisor can relay traffic between the outside network and the lab LAN, outside pfSense

Date: 23-24/10/2026 · Type: configuration finding (audit) · Severity: medium to high · Link: F-01 (host on the LAN), EBIOS scenario SO-3
Asset: hypervisor HV01 (host TeneT, Fedora Linux 44) — interfaces wlo1 (outside network: home or phone hotspot) and br-tenet (bridge of the LAN 10.10.10.0/24, host address .2), host firewall firewalld

Finding

Three conditions met, observed on 23/10:

  1. The host routes packets: net.ipv4.ip_forward = 1 (required by the libvirt NAT on virbr0, pfSense's WAN side).
  2. The host has a leg in each network: 10.10.10.0/24 on br-tenet (src 10.10.10.2) and 192.168.1.0/24 on wlo1 (src 192.168.1.188).
  3. br-tenet and wlo1 are in the same firewalld zone public, whose intra-zone forwarding is on (firewall-cmd --zone=public --query-forward → yes). The zone also opens the host's ssh service to the LAN.

Risk

A machine on the outside network that adds the route "10.10.10.0/24 via the host" can send packets straight into the lab LAN, without going through pfSense, the only crossing point planned by the architecture. Server replies go back through their pfSense gateway; pfSense's stateful filtering breaks TCP connections in practice (asymmetric routing), but that is a side effect, not a protection. The other way round, any LAN machine reaches the host's SSH service (pivot to the hypervisor, F-01).
Limit of the proof: finding established on the configuration (rules and routing tables), without exploitation from a second machine on the home network.

Checks before fixing

  • lsmod | grep br_netfilter: module not loaded; net.bridge.bridge-nf-call-iptables absent. Traffic between VMs on the bridge stays at layer 2 and does not cross the host firewall: changing the bridge's zone cannot cut DC, TrueNAS, fedora exchanges.
  • firewall-cmd --list-all-policies: no active forwarding policy between zones (gateway-* disabled); the libvirt zone (virbr0) is managed separately.
  • ss -tunap on the host: every connection on 10.10.10.2 is outbound (browser to Zabbix, Grafana, Prometheus, TrueNAS, pfSense); prometheus.yml does not scrape the host. Nothing in the lab needs to reach the host.
  • Return point: snapper -c root create -d "PRE-F13-ZONE-LAB" (snapshot 188, 24/10 01:10).

Fix

A dedicated zone for the lab bridge, with no service and no forwarding, attached by NetworkManager (persistent):

firewall-cmd --permanent --new-zone=lab-tenet  
firewall-cmd --permanent --zone=lab-tenet --remove-forward  
firewall-cmd --reload  
nmcli con mod br-tenet connection.zone lab-tenet  
nmcli dev reapply br-tenet

Proof

  • firewall-cmd --get-active-zones: lab-tenet → br-tenet; public → wlo1 only.
  • lab-tenet: target: default, services: empty, forward: no (--query-forward → no).
  • From the LAN (VM fedora), 24/10 02:05, host reachable (address restored): 10.10.10.2:22 closed, 10.10.10.2:9090 closed; controls 10.10.10.20:445 open, 10.10.10.40:55000 and :1514 open. The zone closes the host's services to the LAN without hindering the lab.
  • A first test (01:11) happened during INC-10, while the host had no LAN address; it is not kept as proof.
  • Incident during the change: see INC-10 (non-persistent host address, revealed by the reapply).
  • After INC-10: zone lab-tenet active on br-tenet with the address 10.10.10.2/24 declared in NetworkManager; the host still reaches the lab (ping 0 % loss, Zabbix 200 OK).
  • Stability point: POST-F13-ZONE-LAB-STABLE.

Effect on F-01

The "LAN can reach the hypervisor" leg is closed. The other leg remains: the host still has an address in the LAN and can reach it (admin browser). The full treatment remains measure M-01 (separate administration network). Accepted consequence: administering the host through the WireGuard tunnel is no longer possible; the hypervisor was outside the scope of remote access.

Lesson

(1) One firewalld zone per trust network: two networks of different levels in the same zone make an open bridge. (2) On a hypervisor, ip_forward is often mandatory; so it is the firewall that must say where forwarding is allowed. (3) Before hardening, measure the dependencies (ss, collector configuration, br_netfilter): the fix cut no service.

F-14 — Availability: the SIEM vulnerability database fails to update when the lab starts out of order

Period: 03/10 → 11/10/2026 (finding on 24/10) · Type: finding (CP8), fixed (CP9) · Severity: medium
Assets: VM wazuh-siem (vulnerability-scanner module, CVE feed), Win-Server-DC (the lab's only DNS), VM start-up on the hypervisor HV01

Finding

The Wazuh log, archived at rotation in /var/ossec/logs/wazuh/2026/Oct/ossec-23.log.gz (and not in ossec.log, emptied at midnight), contains 7 content-updater … Could not resolve hostname failures (14 lines: one warning and one error per failure) between 04/10 08:37 and 11/10 07:59 UTC.

Correlation

journalctl --list-boots on the SIEM: each failure happens 47 to 48 s after the VM boots (04/10, 05/10, 06/10, 07/10 ×2, 10/10, 11/10). The first feed download starts before the domain controller, its only DNS server, answers. On 21 and 23/10 the DC was already up: no failure. Two boots (04/10, 9 h of uptime; 06/10, 5 h 30) were followed by no success: from 03/10 09:18 to 05/10 18:45 UTC, the CVE database was not updated, with no alert.

Root cause

No start order: no VM starts automatically, they are started by hand. Ubuntu (SIEM) boots faster than Windows (DC) and depends on its DNS.

Fix

Script /usr/local/bin/lab (root:root, 0755, hash checked):

  • lab start: pfSense, wait for 10.10.10.254:443; DC, wait for a real DNS answer (status: NOERROR and at least one record for infrasec.local); then TrueNAS, fedora, wazuh-siem, wg-client;
  • lab stop: clean ACPI shutdown in reverse order, never forced (also removes the cause of INC-11, the PID file left by a brutal stop);
  • every step logged: journalctl -t lab.

On the DC: shutdown accepted from the logon screen (shutdownwithoutlogon = 1, power button = shut down). Access reserved to whoever has the VM console, hence already administrator of the hypervisor.

Defect found during the test (fixed)

First run: DC DNS operational (0 s), two seconds after Windows started. The test only checked that dig printed something, and dig also prints its failure messages. Fixed (NOERROR and an answer required), checked on three simulated cases (no answer, SERVFAIL, valid answer).

Proof (24/10 and 25/10)

  • lab start: real DNS wait of 35 s, SIEM started 20 s after the DNS answered (24/10 13:24:46 → 13:25:06; same result on 25/10).
  • SIEM: module started at 11:25:20 UTC, no resolution error at the moment it used to happen; feed up to date (Feed update process completed).

Open point, followed in F-26

The DC ignored the shutdown request three times: 24/10 13:43 (180 s), 26/10 00:20 (180 s, stopped on its own after the delay), 26/10 20:32 (300 s, updated script). The script never forced anything. Cause and fix: F-26.

Script evolution (26/10)

lnx-dc01 added to the order (started after the Windows DC, with a wait for a real answer from its DNS); Windows DC shutdown wait raised to 300 s. Hash 825baad6…, previous copy kept (24/10). Shutdown test: five VMs stopped cleanly in order (including lnx-dc01 in 5 s), two refusals reported with no forced stop (F-26).

Lesson

(1) An undeclared dependency (DNS) turns a start order into a silent outage. (2) Logs rotate: an investigation also covers the archives. (3) An availability check must require a real answer, not a non-empty output: "0 s" was the sign that the test could not fail.

F-15 — The SIEM has no host firewall: all its services are open to the LAN

Date: 25/10/2026 · Type: audit finding (CP8), fixed (CP9) · Severity: medium
Asset: VM wazuh-siem (10.10.10.40, Ubuntu 26.04.1 LTS, Wazuh 4.14.8)

Finding

ufw status → inactive. ss -tlnpu shows seven services listening on all interfaces (0.0.0.0 / *): agent reception (1514), enrolment (1515), API (55000), dashboard (443), SSH (22), Cockpit (9090) and node-exporter (9100, added the same day). Only the indexer (9200) and its cluster port (9300) listen locally. Any LAN machine, and the WireGuard tunnel's admin profile allowed into the LAN, can therefore reach the SIEM's administration.

Risk

The SIEM is the machine that detects attacks: compromising it blinds the lab. Exposing its API, dashboard and SSH to the whole LAN widens the attack surface with no business need (least privilege not applied, ISSP network article).

Analysis of legitimate flows (before any rule)

Port Service Real need
1514, 1515 agents, enrolment LAN agents (fedora, dc01, future workstations)
55000 API dashboard (local) and Zabbix check (10.10.10.30, INC-11)
443, 22, 9090 dashboard, SSH, Cockpit administrator from the host (10.10.10.2)
9100 node-exporter Prometheus (10.10.10.30)
9200, 9300 indexer local only (already the case)

Fix

Return point: VM snapshot pre-ufw. Default policy deny incoming / allow outgoing, seven commented rules, one per legitimate flow, logging low, then ufw enable (enabling keeps the open SSH session, allowed by rule 1). Documented emergency path: KVM console then ufw disable.

Proof (25/10, 12:01-12:02)

  • From fedora (10.10.10.30): 1514, 55000, 9100 open; 22, 443, 9090 closed.
  • From the host (10.10.10.2): 22, 443, 9090 open; 9100 closed.
  • Agents fedora and dc01 still Active (agent_control -l).
  • A first test run from the SIEM itself showed everything "open": a connection to its own address goes through the loopback, always allowed. That test could not fail; it is not kept.

Lesson

(1) List the legitimate flows before writing the first rule: each port opens to the only source that needs it. (2) A filtering test is run from a third machine, never from the target. (3) A firewall is enabled remotely with the admin access rule already in place and an emergency console.

F-16 — The SIEM disk is not monitored (and a false growth alarm)

Date: 24-25/10/2026 · Type: finding (CP8), fixed (CP7/CP9) · Severity: medium
Asset: VM wazuh-siem (10.10.10.40), disk /dev/vda2 (ext4, 40 GB)

Starting point: an alarm that was a measurement error

On 24/10 the login banner showed 56.1 % usage and df -h / 60 % thirteen minutes later; I had concluded a growth of 1.6 GB in 13 minutes. On 25/10 the same pair of values (56.0 % then 60 %) came back, and two df one minute apart gave 60 % and 60 %. The banner is computed in advance and cached; only df measures the moment. There was no growth.

Analysis

  • du -xh --max-depth=1 /var/ossec/queue: vd = 11 GB (Wazuh CVE vulnerability database), indexer = 910 MB, the rest < 200 MB.
  • /var/ossec/queue/vd exists since 03/10; the CVE database size is normal for this version and stable.

Hardening (26/10, 21:31-21:43): adm.rj with a key only

  • ED25519 key generated on the host (~/.ssh/id_ed25519_admrj, 100 derivation rounds, protected by a passphrase); fingerprint SHA256:… (masquée / redacted).
  • Public key in C:\ProgramData\ssh\administrators_authorized_keys (the file OpenSSH reads for members of Administrators), rights reduced to Administrators and SYSTEM (icacls /inheritance:r).
  • sshd_config (backup .bak-20261026): PasswordAuthentication no, AllowUsers infrasec\adm.rj; syntax validated with sshd -t before restart; Administrator session kept open as a fallback during the change.

Lesson

(1) A tool constraint does not justify undoing a security measure. (2) On Windows, a firewall rule applies to a network profile.

PV-09 — Lab backup: `lab-backup`, immutable local level

Date: 26/10/2026 · Skills: CP7 (backup, continuity), CP9 (protecting backups)
Assets: host HV01 (LUKS + BTRFS disk), 7 VMs, vault ~/coffre

Need and constraint

No full backup of the lab existed apart from the VMs' internal snapshots. No external disk available. Repartitioning the host disk (LUKS + BTRFS) was ruled out: shrinking the encrypted partition is the riskiest possible operation on that disk.

Preparation: clean-up and inventory

  • /vm/iso: 12 useless files deleted (Windows client ISO, duplicates, CoreOS, Parrot, Cloud image), exact names, no wildcard, after checking the disks attached to each VM (virsh domblklist): 74 GB → 19 GB, 7 images kept (one per VM to rebuild, plus virtio-win).
  • Discovery: wg-client is stored outside /vm, in /var/lib/libvirt/images, and depends on a base image (wg-client-base.qcow2, qemu-img info -U). Without this inventory, the backup would have missed it or made it unusable.
  • /vm is a BTRFS subvolume (ID 259); /vm/images has no copy-on-write (attribute C), which does not prevent snapshots.

Design

Script /usr/local/bin/lab-backup (root:root 0755, hash 5ed4dcb1…):

  1. ordered shutdown (lab stop); abort and restart if a VM refuses to stop;
  2. read-only BTRFS snapshot of the /vm subvolume;
  3. annex subvolume: wg-client and its base image, definitions of the 7 VMs and lists of their snapshots, vault (encrypted secrets, pfSense export), lab and lab-backup scripts; then switched to read-only;
  4. SHA-256 hash of each file; repository /srv/lab-backup reserved to root (700);
  5. ordered restart (lab start); retention: 4 backups. Command export /dev/sdX ready: copy of the latest backup to a LUKS2-encrypted USB disk, refusing any non-USB disk.

Proof (26/10, 21:56-22:05)

  • 7 VMs stopped in 67 s, with no failure (guest agent for 5, ACPI for 2).
  • Hashes: 20 annex files + 9 VM disks (21:57 → 22:02).
  • Ordered restart, DNS of both controllers working; backup 20261026-2156 finished at 22:04:58. Total lab downtime: 9 minutes.

Checks afterwards (22:06-22:12)

  • lab-backup list → 20261026-2156 disques:ro=true annexe:ro=true: both parts are immutable.
  • lab-backup verify → intégrité : OK (integrity OK; full recomputation of the hashes in 5 min 30 s).
  • Write test by root: touch /srv/lab-backup/20261026-2156-vm/test → Read-only file system.

Stated limit

Local level only: protects against mistakes, corruption and ransomware (read-only), not against failure or theft of the host disk. The external level (lab-backup export) waits for a USB disk.

Lesson

(1) A backup starts with an inventory: what we do not know exists, we do not back up. (2) A backup that can be modified can be encrypted by ransomware: read-only. (3) State exactly what a backup protects against, and what it does not.

PROC-01 — Procedure for migrating the directory to `infrasec.internal`

Trigger: end of the Windows Server 2025 evaluation (around 27/03/2027; one last rearm possible, deadline around 09/2027 at the latest), or permanent loss of the dc01 controller.
Goal: employees get their accounts, groups and share access back on the Samba domain, with no loss of data or traceability.
Starting state (26/10/2026): domain infrasec.internal in service, same company (same employes.csv, hash 7228c38a…), same password policy, Wazuh agent active, cross DNS resolution in place (PV-08).

Risk register

Risk Likelihood Impact Measure
Windows evaluation expires: hourly shutdowns, then directory unavailable certain (known date) high: authentication, shares, GPO continuity domain ready; switch planned at least 1 month ahead
The two directories drift apart (accounts created on one side only) medium medium a single source: employes.csv, replayed on both sides (idempotent scripts)
GPOs lost in the switch (Samba does not take over Windows GPOs) certain medium critical GPOs listed (F-17 browsing, password policy) and recreated on Samba or enforced by the firewall

Steps

  1. D-30 — Prepare. Snapshots of every VM; export of the pfSense configuration; samba-tool dbcheck with no error; review of the list of Windows GPOs to reproduce.
  2. D-30 — Align the directories. Replay infrasec-samba-societe.sh employes.csv (idempotent); compare both lists of accounts and group members (Get-ADUser / samba-tool user list); differences = 0.
  3. D-15 — Create the share groups. Create the 10 DL_SMB_<share>_RW/RO in Samba with the same GG_ members as on Windows (PV-05 matrix).

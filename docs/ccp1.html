CCP1 · Administering and securing the infrastructure

This part tells the first stage of the project: building the foundation that the evolution in the next chapters relies on. I rebuilt it on a new Fedora 44 hypervisor, machine by machine, in the order set by the dependencies. It has been in service since October 2, 2026, with its five VMs, the directory and the file share.

I first describe the method, then each build step with its commands, its acceptance check and the problems I ran into. Next come a sheet for each machine, then day-to-day administration, organized by the four skills of the certificate: good practice and operating procedures (CP1), the network (CP2), the systems (CP3) and virtualization (CP4). As in the rest of this report, I only state what I actually did and checked. When the execution departed from the build plan, I say so and explain why. What the lab does not cover is listed at the end.

The foundation at a glance

Everything runs on a single physical machine, an ASUS ROG Strix G18 (32 GB of RAM, NVMe SSD encrypted with LUKS, BTRFS with Snapper snapshots). It is the hypervisor, running Fedora 44 with KVM/QEMU and libvirt. I administer it with Cockpit and from the command line.

Two virtual networks shape the whole. On the WAN side, the libvirt NAT network 192.168.122.0/24 (switch virbr0). On the LAN side, an isolated bridge, br-tenet, carries the internal segment 10.10.10.0/24. Among the VMs, only the firewall is connected to both. The host itself still has an address on the LAN: this is finding F-01, covered below. The diagram below shows the physical architecture (it is also Figure 3 in section 3.4); the reference network diagram, with its flow matrix, is in Annex N.

The five VMs run at the same time within a memory budget set at 22 GB out of 32, which leaves the host the headroom it needs.

Why these choices. KVM is the hypervisor built into the Linux kernel: QEMU emulates the hardware of each VM, and libvirt provides a single interface to define them, start them, back them up and connect them to networks. Fedora brings a recent kernel, SELinux on by default and Cockpit, in the same family as Red Hat Enterprise Linux, which is common in companies. pfSense is an open-source firewall widely used in small organizations. Windows Server remains the standard for the directory. TrueNAS SCALE brings ZFS, which protects data integrity. Wazuh is a complete open-source SIEM. Each building block is therefore representative of what is administered in production.

The build method

An order set by dependencies. The LAN is isolated: nothing on it reaches the Internet until the firewall routes. The domain controller then provides the DNS and the time that TrueNAS needs to join the domain. The build order follows from that:

pfsense-fw  ->  Win-Server-DC  ->  truenas  ->  fedora  ->  wazuh-siem
(gateway)       (DNS, directory)   (joins AD)   (containers)  (SIEM)

During installs, each machine uses pfSense as its gateway and DNS resolver. As soon as the directory is in service, the servers’ DNS switches to the domain controller (10.10.10.10), because Kerberos needs to find its service records.

One acceptance check per step. A machine is not finished until its acceptance test is green: nobody moves on with a red check. The check is always a test that proves the service, not a status light: a DNS query that answers, a verified domain join, a metric that comes through.

A snapshot at every passed check. Two kinds of restore points, always named the same way:

# VM: cold snapshot, for a consistent state
sudo virsh shutdown <vm>; sleep 25
sudo virsh snapshot-create-as <vm> <label> "<description>"
sudo virsh start <vm>

# host: after any change to packages, network or SELinux
sudo snapper -c root create -d "POST-<OPERATION>-STABLE"

A snapshot taken with the VM stopped is consistent: no write is in progress. This is essential for the domain controller, whose database must not be frozen in the middle of a transaction.

Step 1 · The TeneT host

The host is the foundation of everything else: if it is badly prepared, no VM starts or the disks degrade. So I treated its installation like that of a production server. The disk is encrypted with LUKS from the Fedora installation onward: if the machine is lost or stolen, the VM disks cannot be read.

Packages. I only install what is used: virtualization, its administration, containers, SELinux and snapshots, plus a few network tools.

sudo dnf upgrade --refresh -y
sudo dnf install -y qemu-kvm libvirt libvirt-daemon-config-network virt-install \
  edk2-ovmf swtpm libosinfo guestfs-tools \
  cockpit cockpit-machines cockpit-podman cockpit-storaged cockpit-selinux \

libvirt services. Fedora 44 splits libvirt into modular daemons, started on demand by systemd sockets. I enable each socket, then add my account to the libvirt and kvm groups so I can administer without being root for every command:

for d in virtqemud virtnetworkd virtstoraged virtinterfaced virtnodedevd; do
  sudo systemctl enable --now ${d}.socket
done
sudo systemctl enable --now virtlogd.socket cockpit.socket firewalld
sudo usermod -aG libvirt,kvm "$USER"

Dedicated subvolumes. VM disks and container layers each have their own BTRFS subvolume, /vm and /var/lib/containers. This keeps them out of the system snapshots and lets me give them their own options. The most important one is the NOCOW attribute (chattr +C). A qcow2 file is rewritten constantly; on a copy-on-write file system it fragments and performance collapses. The attribute is not retroactive: it must be set on the empty directory, before the first image is created.

sudo btrfs subvolume create /vm
sudo btrfs subvolume create /var/lib/containers
sudo chattr +C /vm /var/lib/containers
lsattr -d /vm /var/lib/containers        # must show the C attribute

Both subvolumes are mounted from /etc/fstab, with the UUID of the root file system:

UUID=<UUID> /vm btrfs subvol=vm,nodatacow,noatime 0 0
UUID=<UUID> /var/lib/containers btrfs subvol=var/lib/containers,nodatacow,noatime 0 0
sudo systemctl daemon-reload && sudo mount -a
findmnt -t btrfs

SELinux, never disabled. This is the step that catches people out most: without it, no VM starts, and libvirt’s error message does not mention SELinux. The images must carry the virt_image_t context. I declare the rule permanently, then apply it. The directory can only be traversed by its owner and the authorized services (chmod 711):

sudo mkdir -p /vm/images /vm/iso
sudo semanage fcontext -a -t virt_image_t '/vm/images(/.*)?'
sudo restorecon -Rv /vm/images
sudo chmod 711 /vm/images
ls -dZ /vm/images          # expected: system_u:object_r:virt_image_t:s0

The rule declared with semanage survives a full relabel of the system; a plain chcon would have been lost at the next restorecon.

The storage pool. A libvirt pool named tenet points to /vm/images. I tested it end to end with a throwaway image, which must inherit both the SELinux context and the NOCOW attribute:

sudo virsh pool-define-as tenet dir --target /vm/images
sudo virsh pool-build tenet && sudo virsh pool-start tenet && sudo virsh pool-autostart tenet
sudo qemu-img create -f qcow2 /vm/images/test.qcow2 1G
ls -Z /vm/images/test.qcow2 && lsattr /vm/images/test.qcow2
sudo rm /vm/images/test.qcow2

The two networks. The libvirt default network (NAT, 192.168.122.0/24, switch virbr0) is the WAN: the host acts as its router and translates addresses to the Internet. A second network, tenet, is an isolated bridge (br-tenet) with no routing to the outside: it carries the LAN 10.10.10.0/24, and its only way out is the firewall. I check both with sudo virsh net-list --all, which must show them active and set to start automatically.

Cockpit. Fedora’s web console replaces virt-manager. From a single interface it creates VMs, opens their consoles, manages snapshots, containers and storage, and shows SELinux denials in plain language, with a suggested fix. It has one trap: when creating a VM, it offers /var/lib/libvirt/images by default. The tenet pool must be chosen explicitly, otherwise the disk loses both the SELinux context and the NOCOW attribute. After every creation I therefore check ls -Z /vm/images and lsattr /vm/images/*.qcow2.

Snapper. The host takes its own restore points. I configured Snapper on the root, with bounded retention and its timers, then took the baseline point of the foundation:

sudo snapper -c root create-config /
sudo snapper -c root set-config NUMBER_LIMIT=10 NUMBER_LIMIT_IMPORTANT=5
sudo systemctl enable --now snapper-timeline.timer snapper-cleanup.timer
sudo snapper -c root create -d "POST-SOCLE-FEDORA-TENET-STABLE"

The /vm and /var/lib/containers subvolumes are not included in the root snapshots: rolling the system back never rolls back the VM disks, which have their own snapshots.

What to understand. KVM turns the Linux kernel into a hypervisor: each VM is a QEMU process that emulates its hardware, and the processor instructions run directly thanks to the virtualization extensions. libvirt drives the whole and provides the virtual networks. A NAT network gives the VMs a way out to the Internet behind the host’s address, without making them reachable from outside. An isolated network has no way out at all: this is why the firewall must be the only machine connected to both. Finally, SELinux labels every QEMU process and every disk: a process can only open the files that carry its label.

Step 2 · The pfSense firewall

The VM. I created it from Cockpit, in the tenet pool, with two virtio network cards: the first on the default network (WAN), the second on tenet (LAN). The Netgate installer installs pfSense CE. The VM was first created under the name tenet-pfsense. I renamed it pfsense-fw to keep the lab’s naming convention:

sudo virsh shutdown tenet-pfsense
sudo virsh domrename tenet-pfsense pfsense-fw
sudo virsh start pfsense-fw

Interfaces. From the console (menu 1, then 2): vtnet0 becomes the WAN, on DHCP from the libvirt NAT (it gets 192.168.122.95); vtnet1 becomes the LAN, at 10.10.10.254/24. I then check the way out to the Internet from the pfSense shell (menu 8):

ping -c3 1.1.1.1
host cloudflare.com

Once the installation is confirmed, I eject the media, so that a reboot never starts the installer again:

sudo virsh domblklist pfsense-fw                   # find the CD drive
sudo virsh change-media pfsense-fw sda --eject --config

The setup wizard. In the web interface (System → Setup Wizard), the firewall gets its name, fw01, and its DNS domain, infrasec.lab, kept separate from the Active Directory forest infrasec.local so that the two are never confused. The administration password is typed interactively and written nowhere in the report.

Filtering. The principle is deny by default:

SettingPathValue
WAN rulesFirewall → Rules → WANNone: all inbound traffic is denied
LAN rulesFirewall → Rules → LANExplicit outbound: DNS, updates, log and metric
forwarding
Log of denied trafficStatus → System Logs → FirewallChecked during every test

Segment services. pfSense runs the segment’s DNS resolver (Services → DNS Resolver, Unbound). Once the directory is in service, the infrasec.local zone is held by the domain controller, and pfSense forwards it (security policy, article 6.5). It also runs the NTP service (Services → NTP): it is the segment’s time reference, which the domain controller syncs with.

Backing up its configuration. The pfSense XML export (Diagnostics → Backup & Restore) is encrypted with a passphrase and stored offline. It never goes into the report: it contains the hash of the administration password and the TLS key of the web interface. This recovery was tested on October 11 (PV-04, Annex O): after a test change, the full configuration was restored from the export in less than five minutes, with the service verified end to end.

Acceptance check. From the LAN, the Internet answers and names resolve. From the WAN, the administration interface cannot be reached. The CD drive is empty.

A gap found later. The October 4 audit showed that the administration interface still answered over HTTP on port 80, in addition to HTTPS (finding F-02). The fix is scheduled: force HTTPS and restrict the management source (Annex F).

What to understand. pfSense is a stateful firewall: when an outbound connection is allowed, the replies that belong to it are accepted automatically. So it is enough to allow specific outbound traffic and deny everything inbound. By default, the Unbound resolver works in recursive mode: it queries the root DNS servers itself, without depending on a provider. Giving the firewall a DNS domain separate from the forest prevents a firewall host name from being confused with a directory record.

Step 3 · The domain controller

The VM. Windows Server 2025 runs with a virtio disk and network card, the fastest options under KVM. Windows cannot see a virtio disk without a driver: when choosing the installation disk, I load the viostor driver from the virtio-win ISO, mounted as a second drive. I open the Cockpit console before the first boot, so as not to miss the boot-from-CD prompt.

Network and name. In an elevated PowerShell, a fixed address, DNS pointing to itself (the future DNS server of the domain), then the name DC01:

New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 10.10.10.10 `
  -PrefixLength 24 -DefaultGateway 10.10.10.254
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 127.0.0.1
Rename-Computer -NewName "DC01" -Restart

Promotion. I install the AD DS role, then create the infrasec.local forest with integrated DNS. The restore mode (DSRM) password is typed interactively: it goes through neither a file nor the history.

Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
$dsrm = Read-Host -AsSecureString "DSRM password"
Install-ADDSForest -DomainName "infrasec.local" -DomainNetbiosName "INFRASEC" `
  -InstallDns -SafeModeAdministratorPassword $dsrm -Force

The server restarts as a domain controller: it holds the forest, the domain, the global catalog and the directory-integrated DNS zone. I check all of it with four commands, which I run again after every change:

Get-ADDomain | Select-Object Forest,DNSRoot,DomainMode
Get-ADForest  | Select-Object ForestMode,GlobalCatalogs
nltest /dsgetdc:infrasec.local
Resolve-DnsName infrasec.local
CommandWhat it proves
Get-ADDomainThe domain exists, with its DNS root and functional level
Get-ADForestThe forest is in place and the controller is a global catalog
nltest /dsgetdcA client finds a domain controller through DNS
Resolve-DnsNameThe infrasec.local zone answers

Time. Kerberos refuses any authentication beyond a 5-minute skew. The domain controller is the time reference of the domain; it syncs itself with pfSense. I had not set this up at first, and it made the TrueNAS join fail (INC-02, step 4): the controller’s time zone was wrong.

Accounts. A service account is dedicated to joining TrueNAS to the domain. A group carries access to the file share: rights follow groups, never individuals. Passwords are typed interactively. Since INC-02, accounts used across several platforms only use characters that sit in the same place on French and US keyboards (security policy, article 5.4.3).

A lab trick. The Cockpit noVNC console does not allow pasting text into the VM. To avoid retyping a script, I serve it from another node through a temporary HTTP server and run it on the controller. This is for the lab only: in production, one goes through an administrative share or a deployment tool.

Agents. The Wazuh agent installs from an MSI. I use an installation that waits for the installer to finish, so that the service is only started once the installation is complete:

Start-Process msiexec.exe -Wait -ArgumentList '/i','C:\path\wazuh-agent.msi', `
  'WAZUH_MANAGER=10.10.10.40','WAZUH_AGENT_NAME=Win-Server-DC','/qn'
Start-Service WazuhSvc
Get-Service WazuhSvc

The windows_exporter metrics exporter (port 9182) took more work. Version 0.31.8 removed two collectors that my plan asked for (cs and logon): the service stopped as soon as it started, with no message (INC-03). Running it in the foreground gave the error unknown collector cs, then unknown collector logon. I wrote a script that tests the set of collectors, removes the ones the service rejects, then reconfigures the service. The final set includes ad and dns, specific to the domain controller role:

msiexec /i windows_exporter.msi `
  ENABLED_COLLECTORS="cpu,logical_disk,net,os,service,system,memory,process,tcp,ad,dns" `
  /qn
Get-Service windows_exporter
Invoke-WebRequest http://localhost:9182/metrics -UseBasicParsing |
  Select-Object -Expand Content | Select-String windows_

A rule specific to the domain controller. It is never stopped with virsh destroy: a hard power-off can corrupt the Active Directory database. Always virsh shutdown, and a cold snapshot before any risky operation.

What to understand. An Active Directory forest contains one or more domains; each domain controller holds a copy of the database. The global catalog makes it possible to find an object anywhere in the forest. Clients do not find the controller by its name: they query DNS for service (SRV) records, such as _ldap._tcp.dc._msdcs.infrasec.local. This is what nltest /dsgetdc checks, and it is why every server in the domain must use the controller’s DNS. Kerberos authenticates with time-stamped tickets: beyond a 5-minute skew, a ticket is treated as a replay and refused. Finally, DSRM mode starts the controller outside the directory to repair or restore it: its password is a critical secret.

Step 4 · TrueNAS storage

The VM. Three virtio disks: a 16 GB system disk and two 40 GB data disks for the ZFS mirror. The system disk stays separate from the data, so that TrueNAS can be reinstalled without touching the pool.

sudo virt-install --name truenas \
  --disk path=/vm/images/truenas-os.qcow2,size=16,format=qcow2,bus=virtio \
  --disk path=/vm/images/truenas-d1.qcow2,size=40,format=qcow2,bus=virtio \
  --disk path=/vm/images/truenas-d2.qcow2,size=40,format=qcow2,bus=virtio \
  --cdrom /vm/iso/<truenas-scale>.iso --network network=tenet,model=virtio \
  --graphics vnc --noautoconsole

First incident: the installer does not start (INC-01). The VM stayed stuck on the UEFI firmware (OVMF) menu, “Please select boot device”. The firmware did not pick the CD drive despite the boot order, and the Cockpit web console did not pass the Enter key through. Sending the key from the host (virsh send-key) failed too, because the VM had stopped in the meantime. I switched the VM to BIOS firmware (SeaBIOS): in its XML definition, I removed the <firmware> block, the <loader> and <nvram> elements and the firmware='efi' attribute of the <os> section, then redefined the VM:

sudo virsh dumpxml truenas > truenas.xml     # UEFI elements removed
sudo virsh define truenas.xml
sudo virsh start truenas

SeaBIOS booted straight from the CD, and the TrueNAS SCALE 25.10.7 installer started. Since then, I choose BIOS for VMs whose installation goes through the web console.

Installation and network. TrueNAS installs on the 16 GB disk. From its console, I give it a fixed address 10.10.10.20/24, the gateway .254 and the domain controller as DNS, 10.10.10.10: Kerberos needs the domain’s DNS to find its service records.

The pool. In the web interface (Storage → Create Pool), the tank pool is a ZFS mirror on the two data disks. A mirror survives the loss of a disk. ZFS computes a checksum for every block: it detects silent errors and repairs them from the other copy of the mirror, provided a regular scrub runs.

Joining the domain. In Credentials → Directory Services, I enter the domain INFRASEC.LOCAL, the dedicated service account and its password, typed interactively. This is where the second incident happened.

Second incident: the join is refused (INC-02). The first attempt was refused: “Time offset from the domain controller exceeds the maximum permitted value”. I compared the clocks from the host with virsh domtime. TrueNAS was on the correct UTC time; the domain controller was more than 5 minutes off, because of a wrong time zone. After fixing the time zone and syncing the controller to pfSense over NTP, a second error appeared: “The bind password is not correct”. The join account’s password had been typed on two different keyboard layouts (QWERTY and AZERTY), which produced two different strings. I reset the password with neutral characters, and the join succeeded. The TrueNAS Active Directory service went to HEALTHY: realm INFRASEC.LOCAL, machine account keytab created, account cache enabled.

The share. The tank/partage dataset carries the SMB share partage (Shares → Windows (SMB) Shares). Access is controlled by NFSv4 ACLs, set in the dataset’s permission editor and granted to the Active Directory group created for it.

Data protection. In Data Protection:

TaskSetting
Periodic snapshots of tank/partageEvery hour, kept two weeks, named auto-%Y-%m-%d_%H-%M (visible in
Windows Previous Versions)
ReplicationTo tank/partage_backup, with zfs send and zfs recv
Scrub of the tank poolScheduled, to verify every checksum

Acceptance check. From the TrueNAS shell (System Settings → Shell), the join is proven through Kerberos, not only through access to the share:

wbinfo -t              # trust relationship with the domain: OK
net ads testjoin       # join is valid
zpool status tank      # mirror ONLINE, 0 errors

The restore was then proven by report PV-01 (Annex G): three files deleted, then restored in less than one second, with matching SHA-256 hashes.

What to understand. With two data disks, a mirror is the only redundant layout: every block is written to both disks. ZFS always writes changed data to a new location (copy on write). A snapshot is therefore instantaneous: it freezes the list of blocks at a given moment and only takes space for the blocks changed afterwards. It is read-only, which protects it from deletion or from encryption by ransomware on a client. NFSv4 ACLs are finer than POSIX permissions (inheritance, separate read, write and delete rights) and map to Windows ACLs, which makes them a natural fit for an SMB share. Joining the domain creates a machine account in the directory and a keytab, the key file that lets TrueNAS authenticate with Kerberos.

Step 5 · The container node

             fedora

The VM. Fedora 44 Server, at the fixed address 10.10.10.30/24, gateway .254, DNS .10. It is administered through Cockpit (port 9090) and SSH. It also serves as the audit workstation: the Parrot VM planned for the audit never booted, and the October 4 audit was run from this node.

An unprivileged account for containers. Containers run under the ais account, without root rights. Rootless Podman relies on UID and GID ranges delegated to this account (/etc/subuid, /etc/subgid): root inside a container maps to an unprivileged user on the host. systemd lingering lets the account’s services run without an open session:

sudo loginctl enable-linger ais
grep ais /etc/subuid /etc/subgid
mkdir -p ~/.config/containers/systemd

Services described by Quadlets. Each container is described by a .container file in ~/.config/containers/systemd/. systemd generates a user unit from it: automatic start, restart on failure, logs in journalctl. These files are the reference: image, published port, volumes, arguments. node_exporter shows a special case. It must read the host’s file system, but /proc and /sys cannot be relabeled for SELinux with the :Z option. So it shares the host’s network and mounts the root read-only:

[Unit]
Description=Prometheus node-exporter (rootless)
[Container]
Image=quay.io/prometheus/node-exporter:latest
Network=host
Volume=/:/host:ro,rslave
Exec=--path.rootfs=/host --collector.systemd
[Install]
WantedBy=default.target
systemctl --user daemon-reload
systemctl --user start node-exporter
systemctl --user status node-exporter
podman top node-exporter huser # the real UID on the host: not root

The monitoring stack. Prometheus and Grafana run on the same model. The plan put Prometheus on its usual port, 9090, but Cockpit already uses it on this node: I published it on 9091. Grafana listens on 3000. Zabbix, added during the evolution, polls pfSense over SNMP. Configuring the monitoring itself belongs to skill CP7 and is described in section 6.1.

The local firewall. firewalld only opens the ports that are needed. When a port is no longer used, I close it: the node_exporter port (9100) was removed, since Prometheus queries it locally (finding F-05):

sudo firewall-cmd --permanent --remove-port=9100/tcp
sudo firewall-cmd --reload && sudo firewall-cmd --list-all

Acceptance check. systemctl --user status active for each service, podman ps shows the containers, podman top … huser shows a non-root UID, and the metrics answer (curl -s localhost:9100/metrics | head). The hardening of this node is described with skill CP3.

What to understand. A rootless container relies on user namespaces: UID 0 inside the container maps, on the host, to a UID taken from the ais account’s subordinate range, with no rights at all. If an attacker broke out of the container, they would land on an unprivileged account, not on root. For the same reason, a rootless container cannot listen on a port below 1024 by default. Quadlets replace a composition tool: systemd itself starts, watches and restarts the containers, like any other service. The :Z option on a volume asks Podman to give it a private SELinux label, readable by that container only.

CP1 · Operating with good practice

Rules set before acting. At the top of the command booklet, I wrote the rules I do not break. A snapshot before any destructive operation: virsh snapshot-create-as for a VM, snapper for the host. Never a virsh destroy on the domain controller. Never chmod 777: permissions are set through ownership (chown), groups and, for containers, user namespaces. Rootless containers by default. No plaintext secret in a file or a command. And never /var/run/docker.sock mounted into a container without warning about the risk, since it amounts to giving root access to the host.

CP2 · Securing the network

A single point of passage. pfSense is the only VM connected to both the WAN and the LAN. On the WAN side, no inbound connection is accepted by default; the one exception, the WireGuard tunnel port, belongs to the evolution in chapter 5. Denied traffic is logged, which gave me evidence during the tests.

Segment services. pfSense resolves names (Unbound); the infrasec.local zone is held by the domain controller and forwarded by pfSense (security policy, article 6.5). It is also the time reference. The servers have fixed addresses, listed in the addressing plan of the security policy (supplement E.1).

Filtering inside the segment. Traffic between two VMs on the same segment does not go through pfSense. I therefore restricted it on each machine: firewalld on the Fedora hosts, Windows Firewall on the domain controller. The October 4 audit confirms it: on every host, almost all the ports tested are filtered, and no legacy or unencrypted service (Telnet, FTP, SMBv1) is exposed (Annex B).

Troubleshooting layer by layer. For network faults, my method is successive captures: WAN, then the rule counters, then LAN (Diagnostics → Packet Capture). This is what located the two faults of the remote access in a few minutes (INC-06 and INC-07, Annex J). It also taught me that a network test must start from the right place: a test run from the hypervisor, which has a direct route to the segment, “succeeded” without proving anything (INC-05).

What the audit found, and what I did about it. The foundation is not perfect, and I would rather say so. The host keeps an administration address on the production segment, which bypasses the firewall (F-01). The pfSense interface still answers over HTTP on port 80 (F-02). The administration plane can be reached from the whole segment (F-06). Each finding received a written decision: F-01 is temporarily accepted, with a compensating measure and a target, a dedicated administration network (measure M-01); F-02 and F-06 are scheduled (Annex F).

CP4 · Securing virtualization

Isolation through SELinux. SELinux stays in enforcing mode. The disks carry the virt_image_t context, which becomes svirt_image_t while the VM runs: each VM gets its own categories, which isolates it from the others and from the host. If a VM were compromised, it could not read another VM’s disk. If a VM refuses to start, I look for the denial and fix the context: I never disable SELinux.

Virtual networks. The libvirt NAT on the WAN side and the isolated bridge br-tenet on the LAN side. The host still has an address on this bridge: this is finding F-01. It even skewed a test (INC-05), which confirms that a separate administration network is a priority.

Containers. They run rootless, under an unprivileged account, with user namespaces. No daemon socket is mounted into a container, and no container exposes a privileged port (below 1024).

Resources. The memory budget (22 GB out of 32) leaves the host the headroom it needs; free -h after each VM start shows that it is not exceeded. Monitoring of the host and the VMs with Prometheus is described in section 6.1.

Recovery. Each VM can go back to a named snapshot, the host to a Snapper point, and the pfSense configuration to its encrypted export. The operations manual orders these rollbacks from the lightest to the most complete (Annex M, section 8):

sudo virsh snapshot-list <vm>
sudo virsh snapshot-revert <vm> <label>     # back to a known state

Summary of the foundation

The foundation was built in the order of its dependencies, each step closed by a test and a snapshot. It provides a single filtered point of passage, a central identity, storage controlled by groups and a backup proven by a restore. Hardening is measured (Lynis 69 → 76), and every step can be undone. Each of the three build incidents left a rule: BIOS for installations through the web console, time synchronized before any Kerberos join, release notes read before deploying an exporter. Its limits are known, written down and tied to a decision: the host’s address on the segment, administration that is still too open, a SIEM that does not cover every machine yet. It is on this documented and reversible base that I could design and deploy the Zero-Trust remote access (chapters 4 and 5) and manage the security of the whole (chapter 6).
